# apex/ — the capacity dashboards as an Oracle APEX application

The third optional way to look at the suite's numbers, and the only one
that needs nothing outside the database: no Elastic stack, no Grafana, no
REST module. The application is imported into an APEX workspace whose
parsing schema holds the suite, reads the `CAPR_*` views and `CAP_CONFIG`
of that schema, and draws them with APEX's own components (Oracle JET
charts, Interactive Reports, classic reports). No external JavaScript, no
copies of the data, and nothing in the suite's tables is ever written; the
only thing the app writes is its own session state (APEX collections).

```
Oracle   CAPR_SERIES_POINTS / CAPR_FORECAST_POINTS / CAPR_FIT / CAPR_ANOMALIES /
         CAPR_ALERTS / CAPR_CONTAINER (the six contract views), CAPR_TARGETS,
         CAPR_MEM_VERDICT / CAPR_MEM_EVIDENCE / CAPR_MEM_COMP_POINTS
         + CAP_CONFIG                                       (suite views, read-only)
   │     loaded once per APEX session into AWRCAP_* collections
   ▼
APEX     application "AWR Capacity" (apex/awrcap_app.sql, generated by apex/build.py)
         pages: Overview, Targets, Tablespaces, CPU and workload, Memory sizing,
         Fleet anomalies
   ▼
Browser  http://<ords-host>/ords/r/<workspace>/awrcap/overview
```

The same views feed `elk/` and `grafana/`, so all three paths show the same
numbers by construction (`grafana/API.md` documents the shapes).

## When to pick this over `elk/` or `grafana/`

- You already run APEX (it ships with every Oracle database since 19c; ORDS
  serves it) and want the dashboards next to the data with database
  authentication and no new moving parts.
- You want the operator's own ad-hoc analysis: every table here is an
  Interactive Report, so filtering, sorting, grouping and CSV download come
  for free.
- You do not need fleet-wide history of the fits themselves (the ELK path
  snapshots fits and alerts per day; APEX, like Grafana, shows the current
  fit).

Pick `grafana/` when Grafana is already the team's pane of glass, `elk/`
when the fleet is already in Elastic.

## Pages

| page | shows | filters that apply |
|------|-------|--------------------|
| Overview | alert counts by severity, the live alert list, worst days to full, total database size, data freshness | target, database |
| Targets | one row per target and DBID from `CAPR_TARGETS`: feed, host, newest snapshot and its age, stale flag, collect state, last collect and last error, gaps, plus its critical and warning alerts and worst days to full; hours since the newest snapshot as a bar per target | none (it lists every target) |
| Tablespaces | days-to-full ranking, used space with the REGR projection (dashed), its band (dotted), the ceiling (grey) and anomaly days (red); daily growth with flagged days in red; growth anomalies; tablespace alerts | target, database, tablespace, date range |
| CPU and workload | host busy % and busy-hour p95 against the saturation line, DB CPU % per container with level-shift windows, CPU trend fits, SESSIONS / PROCESSES / DB size / redo against their limits with forecasts, I/O requests per second and I/O MB per second (`IOPS` / `IO_MBPS`, daily p95, no limit), workload fits, CPU and series alerts | target, database, date range |
| Memory sizing | the verdict per instance and area (`CAPR_MEM_VERDICT`: grade, current and suggested size, parameter, headline, reason, flags), the SGA component sizes over time (`CAPR_MEM_COMP_POINTS`), PGA allocated against its limit with the forecast, and the evidence behind each verdict (`CAPR_MEM_EVIDENCE`) | target, database, date range (the charts) |
| Fleet anomalies | anomalies per day by kind, most anomalous series, the anomaly timeline per series lane, the anomaly list with drill-downs, every alert | target, database, kind, severity, date range |

Every table that lists series, fits, anomalies or alerts has a **Target**
column: the `target_name` that `CAPR_CONTAINER` gives the row's database.
The **Target** filter narrows every page to one target, and the Database
list to that target's containers. A target name on the Targets page opens
the Overview for that target. A database left selected from another target
is dropped.

The memory verdicts are instance level and filed under the CDB root, like
host CPU: with a PDB selected the Memory sizing page shows its CDB's rows.
They are report content. No alert count includes them.

The filter bar lives on the global page, so a selection carries across
pages. A **Refresh data** button reloads the views; the **Data** badges next
to it show the latest observed day per database and when the data was
loaded, so an empty alert list is never mistaken for missing data.

## Install

Built and tested on APEX 26.2 (Oracle Database 23ai Free). The export uses
the 26.2 import API, so the target instance must run APEX 26.2 or later.

1. **Suite.** Install the suite (`install.sql`, any deploy mode) in the schema
   that will be the application's parsing schema. The app needs the
   `CAPR_*` views from `ddl/45` and `ddl/55` (part of `install.sql`) and
   `CAP_CONFIG`. A suite older than M26.4 lacks the `CAPR_MEM_*` views and
   the Memory sizing page fails to load there.
2. **Workspace.** Create a workspace whose primary schema is that schema and
   at least one end-user account. From SQL*Plus as `SYSTEM` (or any user
   with `APEX_ADMINISTRATOR_ROLE`) in the PDB:
   ```
   SQL> @apex/workspace.sql AWRCAP AWRCAP
   ```
   It creates the workspace if missing, a developer account `ADMIN` and an
   end-user account `AWRCAP_VIEWER` (no App Builder, no SQL Workshop), and
   prompts for their passwords without echoing them (a blank password leaves
   an existing account untouched, so re-running is safe; for a
   non-interactive run pass the two passwords as arguments 3 and 4 with
   stdin from `/dev/null`, never piped). The APEX administration UI does the
   same thing by hand.
3. **Application.** As the parsing schema owner or an APEX administrator,
   from the `apex/` directory (the installer uses relative includes):
   ```
   cd apex
   sqlplus awrcap/...@//host:1521/pdb @install.sql AWRCAP AWRCAP 110
   ```
   Arguments: workspace, parsing schema, application id (defaults `AWRCAP`,
   `AWRCAP`, `110`). The installer refuses to overwrite an application id
   that belongs to another application or workspace, and re-running replaces
   the app in place (existing sessions of the app end).
4. **Open** `http://<ords-host>/ords/r/<workspace>/awrcap/overview`
   (workspace path prefix in lower case; the other page aliases are
   `targets`, `tablespaces`, `cpu`, `memory`, `anomalies`) and sign in with the end-user account.
   `f?p=110` works too.

Lab shortcut for the Docker instance described in `LAB.md`:

```sh
apex/publish.sh          # build.py -> docker cp -> install.sql inside the 23cfree container
```

Overrides: `APEX_CONTAINER`, `APEX_PDB`, `APEX_WORKSPACE`, `APEX_SCHEMA`,
`APEX_APP_ID`. The script never prints the container's `ORACLE_PWD`. After
publishing, run the smoke harness as the parsing schema from the `apex/`
directory: `sqlplus awrcap@... @test/apex_smoke.sql 110` (it creates a
scripted APEX session, loads every collection, runs every region and LOV
query under five filter scenarios, and checks each collection against its
source view; non-zero exit on any failure). The scenario values (a
database, a tablespace, a target) are picked from the loaded data, so the
script runs on any schema; its rows-required checks hold on the demo and
the fixture data.

## Checking the app without APEX

Three checks need no APEX instance. The first two need no database and run
in `test/check.sh`.

- `python3 apex/build.py --check` fails when `awrcap_app.sql`,
  `test/apex_smoke.sql` or `test/apex_probe.sql` is not what the builder
  writes now.
- `python3 apex/test/export_check.py [-v]` parses the export on its own and
  compares it with the builder's registries: every page, region, chart
  series, filter item and collection load once, component ids unique and
  every reference defined, every SQL text extracted and equal to the
  builder's, each query reading only columns its collection defines and
  only collections the loader loads on that page, every report, sort and
  chart column present in its query, and every extracted text present in
  the smoke script and the probe.
- `apex/test/apex_probe.sql` runs the app's SQL on a real install of the
  suite, in the suite's schema, from the repository root:
  ```
  sqlplus awrcap@//host:1521/pdb @apex/test/apex_probe.sql
  ```
  A table `AWRCAP_PROBE_COLL` shaped like `APEX_COLLECTIONS` stands in for
  the collections (created at the start, dropped at the end). The
  application's own loader queries fill it, then every region query, LOV
  and default of every page runs against it under the smoke script's
  scenarios with the filter items bound through `DBMS_SQL`, every row and
  column fetched, and each collection is compared with its source view. A
  link column's `apex_page.get_url` call is replaced by plain text. It
  prints one line per statement, then `RESULT: apex probe <n> passed, <n>
  failed`, and exits non-zero on a failure. On the dbmint VM:
  `test/dbmint_harness.sh <SCHEMA> --no-fixture --sql apex/test/apex_probe.sql`.

What these cannot show: that APEX imports the export, and what a page
looks like in a browser. Only an APEX 26.2 instance shows that
(`install.sql`, then the smoke script).

## How the app reads data

Every `CAPR_*` view is a live evaluation of the forecast and anomaly chain;
on the demo schema `CAPR_ANOMALIES` takes about nine seconds and
`CAPR_FORECAST_POINTS`, `CAPR_FIT` and `CAPR_ALERTS` two to four seconds each.
A page with half a dozen regions would re-run them half a dozen times, so
the app loads each view **once per session** into an APEX collection
(`AWRCAP_SERIES`, `AWRCAP_FORECAST`, `AWRCAP_FIT`, `AWRCAP_ANOMALIES`,
`AWRCAP_ALERTS`, `AWRCAP_CONTAINER`, `AWRCAP_TARGETS`, `AWRCAP_MEM_VERDICT`,
`AWRCAP_MEM_EVIDENCE`, `AWRCAP_MEM_POINTS`, plus `AWRCAP_META` with the
load time and the `CAP_CONFIG` thresholds) and every region reads the
collection. A
page loads only the collections it needs, the first time it is opened in a
session; later visits are instant. On the demo schema the first Overview of
a session takes about 14 s (the anomalies view alone is 9 s), Tablespaces
adds about 4 s for the forecasts, and every later page view is 2 to 3 s.
**Refresh data** drops the collections and reloads them; the load time
(database clock) is shown in the **Data** badges. The loader is the
application process "Load data" (Before Header); it also fills the date
range (last observed day minus and plus 120 days) and, on the Tablespaces
page, picks the tablespace with the fewest days to full when none is
selected. The three memory collections load on the Memory sizing page only.
The timings above were measured before that page and the Targets page
existed. The memory views are the costly ones (`CAPM_VERDICT` took about 8 s
on a real 30-day AWR), so expect the first Memory sizing page of a session
to take longer than the others.

The CTE that maps collection slots back to named columns is generated once
from the registry in `build.py` and prepended to every region query, so a
column is defined in exactly one place.

## Security

APEX account authentication; the end-user account has no development
privileges. The app's SQL touches only the parsing schema's `CAPR_*` views,
`CAP_CONFIG` and the APEX collection API; it exposes capacity numbers and
object names, never row data. Grant the parsing schema nothing it does not
already have for the suite. Put ORDS behind TLS outside a lab.

## Notes and limits

- **Collections hold the whole view.** Fine for one database or a small
  fleet (the demo schema: 3,500 series points). For hundreds of tablespaces
  times a year of history the first page load of a session grows with the
  data; if that matters, materialize the `CAPR_*` views by a job and point
  the app's parsing schema at the copies. The suite's results layer (ddl/60)
  now keeps such copies for the fits and alerts: `CAPR_FIT_HISTORY` and
  `CAPR_ALERTS_LATEST`, refreshed by `cap_results.refresh`; the app does not
  read them yet.
- **Horizon 0 is the anchor**: the current value (for CPU the smoothed
  `anchor_value`), and since M18.1 every REGR horizon in
  `CAPR_FORECAST_POINTS` is `anchor + slope x h`, so the dashed projection
  starts at today's value.
- **ESM points are optional.** The ESM marker appears only when a model
  is fresh (`cap_forecast_ml.train_all`, 30-step cap); the charts never
  depend on it. Its `CAPR_FORECAST_POINTS.horizon_days` is now the model's
  furthest step minus its age (`esm_horizon_days - model_age_days`), not
  always 30.
- **CPU reference lines.** The saturation line is `cpu_sat_pct` from
  `CAP_CONFIG` (80 by default). `CAPR_FIT` and the point feeds all carry it
  as the CPU `limit_value` (and `pct` as a percent of it); the app draws the
  line from the config value.
- **Host CPU is a root-container series.** OSSTAT records under the CDB's
  own `con_dbid`, so with a PDB selected the host CPU chart shows its CDB
  root's rows (the same host) rather than nothing. The seam reads per-PDB
  DB CPU and redo from the `DBA_HIST_CON_*` views (`CAPV_TIME_MODEL`,
  `CAPV_SYSSTAT`); sessions and processes stay CDB-wide under the root (see
  `CLAUDE.md`).
- **Tablespace filter values are `database|tablespace`**, because tablespace
  names repeat across databases; "All tablespaces" draws only the observed
  lines (the projection, band and ceiling need one tablespace).
- **The anomaly timeline draws episodes.** Consecutive flagged days of one
  series and kind merge into one bar; a level shift spans its window.
  Colours are per kind (growth red, CPU amber, shift blue); a kind the app
  does not know keeps the chart's default colour, and the kind and severity
  filters list whatever values the data has.
- **A level shift is dated at the start of its window** (`ts`), with the
  window's last day in `obs_day`; the DB CPU chart shades that span.
- **Alerts are stateless in the app.** `CAPR_ALERTS` is the current
  evaluation. It now carries a stable `state_key`, `direction`,
  `alarm_threshold` and `is_current`, and the suite's results layer adds
  acknowledgement and new / resolved events (`CAPR_ALERTS_LATEST`,
  `CAPR_ALERT_EVENTS`, `cap_results.ack`); the app reads none of them yet,
  so its alert tables are "what pages right now".
- **Region SQL keeps the suite's 19c floor** (inline window clauses, explicit
  formats), so the same export runs against a 19c database that hosts APEX
  26.2.

## Regenerating the application

`apex/awrcap_app.sql` is generated; edit `apex/build.py` and re-run
`python3 apex/build.py --smoke` (the export, the smoke script and the
probe; without `--smoke` only the export, and `--check` then reports the
other two as stale). A new field is one `(column, slot)` pair in
`COLLECTIONS` and one `Col` where it is shown. A new view is one
`COLLECTIONS` entry. A new page is a `Page` in `PAGES` with a new id. The
loader, the navigation, the smoke script and the probe follow from those. Component ids come from a fixed sequential
allocator, so a rebuild is byte-identical unless the builder changed;
inserting a component renumbers the ids after it, so a small builder change
can touch many lines of the export (compare builders, not exports). Page
ids are part of every URL: Targets is 5 and Memory sizing 6 although the
menu lists them earlier. After changing a query run the probe, and the
smoke script where an APEX instance exists.
