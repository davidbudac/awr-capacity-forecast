Architecture

Architecture and data flows

What the suite is made of, where each part runs and how data moves through it. The page starts with the whole system and goes one level deeper in each section. For the mathematics see How it works; for every object and knob see the Reference.

Level 1

The system in one picture

Three parts: the databases that are measured, one database that does the measuring, and whatever reads the results.

  • Measured databases keep their AWR and gain one read-only account. Nothing of the suite is installed there.
  • The repository database copies AWR over a database link, hourly, into tables it owns. Every number in a report is computed by views over those copies. A small results layer stores what a view cannot recompute: history of past fits and the state of each alert.
  • Consumers select from the report views or the results layer: four SQL*Plus report drivers, three optional dashboards, and any monitoring system that can poll a view.

There is one production architecture. A database that measures only itself is a repository with itself as its one target, over a loopback link (Measure one database). The diagram of both deployments is on Getting started.

Level 2

Where it runs: two accounts and a link

AWR lives in CDB$ROOT. The suite lives in a PDB. One database link joins them.

The reader is created by target/prepare.sql (target/self.sql on the standalone path) and checked by target/check.sql. CONTAINER_DATA = ALL matters: without it a common user reading DBA_HIST_* in the root sees only the root's rows. The owner is created by create_owner.sql. Its privileges are granted directly because views and definer's-rights packages ignore roles. Details: A dedicated owner, Repository mode.

The install, step by step

Every installer runs the same scripts in the same order. Only the first one needs the root container.

install.sql itself loads the layers bottom up: The load order. Re-running it is safe: it drops and re-creates every view and keeps every persisted table.

Level 3 · Data in

The collector

cap_repo.collect is the only code that reads a measured database. It copies; it computes nothing.

KindSourcesHow it is copiedPurged?
F fact22, one row per snapshot and key (usage, OSSTAT, time model, …)Appended for the snapshots above the DBID's high-water mark, in chunksAfter repo_retention_days (400)
D dimension5, names and sizes (tablespaces, datafiles, containers, …)MERGEd whole on every collect, null-safe on the keyNever
S scoped dimension1, SEG_STAT_OBJOnly the keys of the segment statistics in the chunkNever
  • Incremental. The window starts at the high-water mark, not at the oldest snapshot, so the copies hold exactly what the target's views showed.
  • Restartable. Rows and mark commit together per chunk. A collect that fails is logged ERROR and the next one continues from the mark.
  • Longer memory than AWR. Copies are kept 400 days by default; stock AWR keeps 8. Tier 2 needs about 120 days, which is why a database measuring itself also copies.
  • Optional sources. Eleven memory sources may be missing from an older reader's grants. Collect skips those with one warning and copies the rest.
  • RAC. The newest snapshot is held back while fewer instances have finished it than the one before. RAC itself is untested.

One manifest, three generated artefacts

Which views are copied, which columns, under which key and filter is declared once.

ddl/13_seam_repository.sql carries three things: the CAP_H_* copy tables (created once, columns only ever added), CAP_REPO_SOURCE (the finished pull statements the collector runs) and the seam views, which are the template with each dba_hist_x renamed to cap_h_x. The copy check proves a copy against its source: Testing.

Level 4

The seam

Twenty-four CAPV_ views are the only place that knows where rows come from.

Thirteen views carry space, CPU, time model, limits, parameters, ASM and segment statistics. Eleven more carry memory statistics and advisors. CAPV_CONTRACT lists the columns the analytics expect, and the installer and doctor.sql check the live views against it. Because both seam files define the same views, the test fixture exercises the same analytics SQL that production runs.

Session scope: one target costs one target

A predicate placed above the seam does not survive the materialized subqueries on the way down, so a report for one target would still read every target's copies. The scope therefore lives at the bottom.

The scope is the dbid parsed from CLIENT_INFO (AWRCAP dbid=<n>). Every source read in both seam files repeats that expression inline, on both sides of a join and in every subquery, because inline parses cheaper than a subquery. CAP_SCOPE is the same expression as a one-row view, for a look at the scope a session has. test/scope_plan.sql explains every view and counts seam reads without the lookup; the count must be zero. Writers (cap_results.refresh, the Tier 2 trainers) clear a scope they find, because they must read every database.

Level 5

The view stack

Six prefixes, one direction. Each layer is plain views over the layer before it.

PrefixFilesGrainHolds
CAPV_ddl/13 or ddl/12snapshotAWR columns under stable names, every row keyed (dbid, con_dbid)
CAPD_ddl/20, 25day; CPU also interval and hourDaily tablespace usage, CPU and DB time, and CAPD_SERIES_DAILY, one shape for every fixed-ceiling series. Tablespace overrides are applied here, once
CAPF_ddl/30, 35, 50seriesOne fit per series: slope, bands, days to full, to saturation or to limit, quality grade. Tier 2 forecast, comparison and backtest
CAPA_ddl/40observation and baseline modeRobust anomaly scores, the CPU level shift
CAPM_ddl/42instance and memory areaMemory sizing verdicts with their evidence
CAPR_ddl/45, 55, 60display rowLabelled sections for the reports, the point feeds, the alert list, and the views over the results tables

The cost of this design is parse time and memory. A session that runs the whole stack holds 1.1 to 1.3 GB of PGA, most of it from parsing deeply nested views, not from sorting (Memory (PGA)). The snapshot cache exists to pay that once a night.

Configuration

A view never reads CAP_CONFIG and never inlines a default. A missing knob therefore shows up as a NULL in CAP_CFG and a MISSING line in CAP_CFG_CHECK, not as a silently different threshold. Per-tablespace ceilings and thresholds live in CAP_TBSPC_OVERRIDE (CAP_TBSPC_OVERRIDE). All knobs: Configuration knobs.

Level 6 · Analytics

The forecast path

Two engines read the same daily series and meet in one comparison view.

  • Tier 1 is SQL: least squares, Theil–Sen or drift, with prediction bands, change-point resets and cycle detection. It exists the moment the views do.
  • Tier 2 is Oracle Machine Learning exponential smoothing. The trainer copies one series at a time into the temporary table CAP_ML_INPUT and lets OML read that, never the views: handed a view, OML planned work that grew with the fleet. A failed build keeps the previous model.
  • Compare lines both up per series; the backtest scores each on held-out days. ESM stops at 30 days on 19c, so long horizons are always Tier 1.

The methods: Forecast quality, Two engines.

Level 6 · Analytics

The anomaly path

One engine scores every series; a separate detector watches for CPU steps.

CAPA_OBS decides what is scored, in which unit and above which floor. CAPA_ANOM compares each observation with its baseline under every mode of its grain: TRAILING and SAME_DOW per day, HOUR_OF_WEEK per CPU hour. The baseline mode is part of the key. CAPR_ANOMALIES owns severity, message and whether a mode alerts; the alert list takes its anomaly rows from there, with consecutive days folded into one episode. The rules: Anomalies.

Level 6 · Analytics

Memory verdicts

One grade per instance and memory area: is it undersized, oversized or fine, and on what evidence.

  • Areas: PGA_LIMIT, PGA_TARGET, BUFFER_CACHE, SHARED_POOL, SGA_TOTAL, SGA_BALANCE.
  • Increments only. Layer 02 turns every cumulative counter and advisor estimate into per-interval increments in one place. Nothing is differenced across a restart.
  • Rules are data. A symptom is a row in layer 05, a grade is a row of the rule table in layer 06. The first matching rule wins.
  • Advisory. A suggestion that would not fit in host RAM or in sga_target is flagged, never reduced.

Query it directly; nothing else in the suite reads these views:

SQL*Plusyou run
SQL> SELECT area, grade, reason,
            ROUND(current_bytes / 1048576)   AS current_mb,
            ROUND(suggested_bytes / 1048576) AS suggested_mb
     FROM   capm_verdict
     ORDER  BY dbid, instance_number, area;

The evidence behind a grade is in CAPM_EVIDENCE. Every view and knob: Object index, Configuration knobs (mem_*).

Level 7 · Data out

Alerts

One view lists everything worth a page. It is computed, not stored.

Each row has two keys. alert_key includes the day and identifies a row; state_key (kind, database, container, series, mode) is stable across days and identifies the condition. Refresh merges on state_key, which is what turns a list that is recomputed every time into states with a history: new, escalated, de-escalated, resolved, reopened, acknowledged.

Level 7 · Data out

The results layer: refresh, LIVE and SNAPSHOT

The one place the suite writes its own conclusions.

  • LIVE is always current and costs the whole stack on every call.
  • SNAPSHOT reads what the last refresh stored: about a second and 10 MB at any fleet size, and as stale as the last refresh. A driver takes LIVE or SNAPSHOT as its last argument (run_report.sh --snapshot).
  • Persisted tables are what refresh adds that no view could: how a fit looked on an earlier day, and when an alert opened, changed and closed.
  • The cache is disposable. Every install drops and re-creates the _S tables empty; the next refresh fills them.

Tables and keys: Persisted tables.

Consumers

Every consumer reads the same views, so a change is made in the view and not in the consumers. Six of them are a contract that only ever gains columns: CAPR_SERIES_POINTS, CAPR_FORECAST_POINTS, CAPR_FIT, CAPR_ANOMALIES, CAPR_ALERTS and CAPR_CONTAINER.
