How it works

Six view layers turn AWR snapshots into forecasts, anomalies, memory sizing verdicts, alerts and a report, on one swappable data source.

The seam

All calculations read from CAPV_ views shaped like the AWR dictionary. Nothing above them reads DBA_HIST_*. Changing the data source means installing a different seam file; everything above it is unchanged. Repository mode runs the code on copies of its targets' AWR, the installing database's own included when it measures itself over a loopback link. Its seam file is generated from repository/seam.sql, the seam written over DBA_HIST_*, with each DBA_HIST_ name swapped for its copy, and a copy check proves each copy equals its source. Fixture mode tests the math against precomputed answers. Until M25 a local mode read the installing database's AWR directly; it is retired.

Every seam read carries dbid = NVL(scope_dbid, dbid). CAP_SCOPE reads the session's CLIENT_INFO (AWRCAP dbid=<n>), which report/scope.sql sets and each driver clears, so a report scoped to one target costs one target at any fleet size. Writers (cap_results.refresh, the trainers) clear a scope they find. Sequence: session scope.

Every analytic window above the seam partitions by dbid: one target's numbers never depend on another's, and a fleet report lists the top top_n of each database.

Layer reference

Columns: object index.

CAPV_  — seam views

Views carrying (dbid, con_dbid). con_dbid is required because TS# restarts at 0 per container (SYSTEM in the root and in a PDB would collide). Block size comes from CAPV_TABLESPACE (populated for every tablespace); the datafile view is a fallback, because DBA_HIST_DATAFILE has no SYSTEM row on stock 19c. CAPV_CONTAINER resolves each (dbid, con_dbid) to a database and PDB name (reports print DB/PDB), CAPV_RESOURCE_LIMIT carries processes / sessions utilisation against the init parameters, and CAPV_SYSSTAT carries the redo size counter and the four physical I/O totals (read and write requests and bytes). CAPV_PARAMETER (cpu_count, FRA size, memory parameters), CAPV_ASM_DISKGROUP and CAPV_SEG_STAT feed the CPU ceiling, the ASM series and "who is filling it"; CAPV_TARGET names each target and its collect health; CAPV_CONTRACT is the column contract doctor checks. Eleven instance-level memory views (M26, filed under con_dbid = dbid) feed CAPM_; they are optional sources, so a target whose reader lacks them still collects. Diagrams: the seam, the collector.

CAPD_  — daily series

Tablespace usage is a level: each day keeps the last sample (KEEP (DENSE_RANK LAST ...)) and converts blocks→bytes. UNDO/TEMPORARY are excluded from the growth series; their daily peaks are the TEMP_PEAK: / UNDO_PEAK: fixed-ceiling series. The tablespace ceiling and operator overrides are resolved here, so every layer above honours them. CPU BUSY/IDLE are cumulative counters, differenced per instance; an interval spanning a restart (startup_time changed) or with a negative delta is dropped. CAPD_COUNTER_DELTA differences every cumulative counter once per interval, with the restart flag, and feeds both interval views REDO_GB_DAY, IOPS and IO_MBPS. Deltas expose day_gap so a multi-day AWR gap becomes a rate, not a spike. CAPD_SERIES_DAILY holds every series with a ceiling, keyed by a series name. CAPD_CPU_INTERVAL and CAPD_DBTIME_INTERVAL hold one row per valid interval, so the daily views and CAPD_CPU_HOURLY (host busy% and per-container DB CPU per clock hour, each bucket labelled by the hour its intervals end in) count the same intervals.

CAPF_  — Tier 1 forecasts

Ordinary least squares over day_n = day_dt − DATE '2020-01-01' (optionally Theil–Sen, see forecast quality). Two fits per series, a 90-day primary and a 28-day recent, give accel_ratio (accelerating growth); it is NULL when the slope is below accel_slope_floor_bpd. days_to_full = FLOOR((limit − cur_used)/slope). CAPA_  — anomalies

Median + MAD, with MAD_σ = MEDIAN(|x − median|)·1.4826. CAPA_OBS lists the observations to score: tablespace growth rates, host busy%, DB CPU per container (per day and per hour), and the fixed-ceiling series. CAPA_ANOM scores each against every baseline mode of its grain in two passes (median, then MAD about it), excluding the point itself from its baseline. CAPA_ANOM_DAY rolls the day modes up to one row per observation. Each flag carries value, median, threshold, robust z and baseline size. Modes: Anomalies: three baselines. CAPA_CPU_SHIFT detects level shifts: CPU: peak, share and shifts.

CAPM_  — memory verdicts

One row per database, instance and area in CAPM_VERDICT: a grade, a reason, the current size and, when a change is advised, a suggested size and its parameter. Areas: PGA_LIMIT (usage against the ceiling), the four advisor areas PGA_TARGET, BUFFER_CACHE, SHARED_POOL and SGA_TOTAL, and SGA_BALANCE (resize activity). Grades: UNDERSIZED / OK / OVERSIZED / INSUFFICIENT_EVIDENCE; for SGA_BALANCE: OK / THRASHING / DRIFTING. The evidence window is the mem_window_days (30) days up to the dbid's newest snapshot. Every counter and advisor estimate is read as increments between snapshots of one startup; nothing is differenced across a restart. CAPM_EVIDENCE holds one row per signal (usage, advisor, symptom, context) with its value, threshold and a sentence. An UNDERSIZED or OVERSIZED suggested_bytes stays within a factor mem_max_step (2) of the current size. exceeds_host_ram flags a suggestion that, with the other side's current size, passes mem_host_ram_pct (80) percent of the host's memory; exceeds_sga flags a buffer cache or shared pool floor under ASMM above what the two pools hold together. A flagged suggestion is never reduced.

Forecast quality: anchors, bands, robustness, resets, cycles, backtests

Each mechanism below is controlled by a CAP_CONFIG knob.

Anchored at today

Projections start at the current value, not the fitted line: proj_h = cur_value + slope · h, with the fit's band half-width around that anchor, so the +30 column and days_to_full agree. For CPU the anchor is anchor_value, the median of the last shift_days complete days.

days_to_full and its range clamp at 0; limit_below_used = 'Y' marks a ceiling below usage (e.g. an override set too low). Every CAPF view carries newest_day and is_current: a series whose last day is more than stale_days (3) behind its source's newest day (a dropped tablespace, a retired database) reads is_current = 'N' and raises no forecast alerts. CPU and redo fits use complete days only (is_complete = 'Y': at least complete_day_pct, 80%, of the day covered by valid intervals).

Prediction bands

Every CAPF_ fit publishes a 95% band per projection from the fit's residuals: resid_se = √(SSE/(n−2)), half-width at horizon x₀ = t · resid_se · √(1 + 1/n + (x₀−x̄)²/SXX).

days_to_full gets a range from the slope's confidence interval (slope_ci = t · resid_se / √SXX): headroom divided by slope + slope_ci is the worst case, by slope − slope_ci the best case (NULL when that slope is not positive). The reports print "120 days, worst case 80".

i

No t-distribution in SQL. Oracle has no TINV, so t ≈ 1.96 + 2.4/df, df = n − 2; good to about 1% for df ≥ 10, and min_train_days guarantees df ≥ 12 before a band is published. The fixture harness computes expected bands with the same expression; change both together.

Theil–Sen

Least squares minimises squared error, so one step (bulk load, import, partition drop) drags the line. Theil–Sen is the median of the pairwise slopes (y_j − y_i)/(x_j − x_i) over the training window (breakdown point 29%). Cost is O(n²), about 4,000 pairs per series at the 90-day window, via a self-join.

slope_method (0 = OLS, default; 1 = THEILSEN; 2 = DRIFT) selects the estimator; a column of the same name records it. The self-join runs only when Theil–Sen is selected, so ts_slope_bpd is NULL under the default. When selected, it drives slope, intercept, projections, days_to_full / days_to_sat, both halves of accel_ratio and the slope = 0 FLAT test, for tablespaces and the CPU trend.

!

The bands stay OLS. There is no closed-form Theil–Sen prediction interval in SQL, so r2, resid_se, the bands and slope_ci remain least-squares residual quantities, drawn around the chosen line.

Drift

For series whose daily growth rate wanders (a random walk), an OLS band is too narrow. With slope_method = 2 the slope is the median of the daily rates and the band is t · (sd · √h + h · se), from the standard deviation of the rates and the standard error of their mean. Quality comes from the slope's confidence interval. drift_slope_bpd / drift_sd_bpd are on every fit regardless of the knob, and CAPF_BACKTEST scores DRIFT too.

Change-point reset

A line fitted across a purge understates the slope and overstates headroom. With reset_on_shrink = 1 (default) the training window restarts at the most recent day whose day-over-day delta is a large negative step:

the ruleM9.3
delta < -GREATEST(shrink_mad_k * MAD_sigma(window deltas), abs_floor_bytes)

abs_floor_bytes stops a flat series (MAD = 0) from treating every wiggle as a cliff. shrink_mad_k defaults to 6, twice the anomaly mad_k. The cliff day is day 1 of the new window (its used_bytes is already post-purge): train_start = reset_day. Both columns are published; reset_day is NULL when nothing reset. If fewer than min_train_days rows remain, quality is INSUFFICIENT_HISTORY. Tablespaces only; a CPU step is handled by CAPA_CPU_SHIFT.

Cyclic tablespaces

With rolling retention a tablespace climbs, is purged, and climbs again. When the training window holds cyclic_min_cliffs (2) or more cliffs, the series is graded CYCLIC: no reset, judged on whether the per-cycle peaks grow. cycle_n, cycle_days, cycle_peak_pct and peak_slope_bpd (a line through the per-cycle maxima) describe it; days_to_full comes off the peak line only when the peaks grow, and TBSPC_FULL fires on that line. Demo: SESSION_STORE, 30-day cycles peaking at 30.8% of its limit, raises nothing.

Backtest

CAPF_BACKTEST hides the last backtest_holdout_days (default 28) of each series, fits the window ending at that cutoff, and reports MAPE and bias against the hidden days, per series per engine. The REGR row is pure SQL, always present, and anchored like the live fit (last value for a tablespace; median of the last shift_days days for CPU, incomplete CPU days excluded). The ESM row appears once cap_forecast_ml.train_backtest has trained purpose = BACKTEST twin models through the same cutoff; twins never feed the live forecast views. The 19c 30-step cap and the FLOOR(rows/4) floor apply to twins, so ESM may cover fewer days than REGR; n_days reports actual coverage.

With esm_tbspc_model = 2 (AUTO, default) and esm_select_by_backtest = 1, each tablespace gets both candidate twins, EXSM_HOLT and EXSM_ADDWINTERS (7-day season), scored in CAPF_ESM_CANDIDATE; the production model uses the lower holdout MAPE (ties or no evidence: Holt). 0 or 1 pins a model type and skips the extra training; esm_select_by_backtest = 0 makes AUTO use Holt.

CPU: peak, share and shifts

Busy hour

CAPD_CPU_DAILY keeps the time-weighted daily average (busy_pct) plus busy_p95 and busy_max over the day's snapshot intervals, and busy_peak_pct, the time-weighted average inside the business-hours window. An interval is in the window when its end hour falls in (peak_hour_from, peak_hour_to]; with hourly AWR and the default (8, 18] that is the snapshots ending 09:00 through 18:00.

CAPF_CPU_TREND fits six metrics per container: BUSY_PCT, BUSY_P95, BUSY_PEAK, DB_CPU_SEC, DB_CPU_PCT and DB_CPU_P95, with the tablespace fit's bands and quality ladder. Percent metrics get a days_to_sat against cpu_sat_pct (default 80); DB_CPU_SEC has no ceiling, so its is NULL. CPU_SAT keys off the p95 trend unless cpu_sat_on_p95 = 0.

DB CPU as a share of the host

CAPD_DBTIME_DAILY derives two percentages from the time-model counters. db_cpu_pct = 100 · db_cpu_sec / (cpu_ceiling · interval seconds) summed per day, cpu_ceiling = LEAST(NUM_CPUS, cpu_count): the container's foreground DB CPU as a fraction of the host's logical-CPU seconds. Oracle accrues CPU per logical CPU and AWR's %Total CPU uses NUM_CPUS; dividing by cores would read 2x on SMT. It is on the busy% scale and forecast the same way. host_share_pct = DB CPU seconds over the host's busy seconds that day. p95 / max / peak-window twins give each PDB its own busy hour. A trend crossing saturation raises DBCPU_SAT.

i

OSSTAT is CDB-wide. Host CPU is recorded under the CDB's con_dbid. In CDB$ROOT, DBA_HIST_SYS_TIME_MODEL holds one CDB-wide row per snapshot; per-container rows are in DBA_HIST_CON_SYS_TIME_MODEL, which the seam reads (the root row is then CDB$ROOT alone). The host busy seconds in host_share_pct's denominator are summed across the dbid, not read per PDB.

Significance gate

On a weekday / weekend host most variance is the weekly rhythm, so R² stays low while load grows and the fit reads LOW_CONFIDENCE. Two knobs, both on by default: cpu_deseason = 1 subtracts the weekday and weekend means (adding back the window mean) before the fit (deseasoned records it); cpu_quality_gate = 1 grades the fit OK when |slope| > slope_ci (slope_sig) instead of R² ≥ r2_gate; 0 restores the R² rule.

hot_now = 'Y' when the median of the recent daily p95 (recent_p95_med) is at or above cpu_sat_pct. It raises CPU_HOT (host) or DBCPU_HOT (container) at any fit quality.

Level shifts

After a step (e.g. 18 points hotter since a workload move) the per-point modes flag a few days, then the step becomes the baseline. CAPA_CPU_SHIFT compares windows: per (container, metric), for BUSY_PCT, BUSY_P95 and DB_CPU_PCT, the median of the last shift_days (7) days against the median of the shift_baseline_days (28) before it. shift_pct is the difference in percentage points, not a ratio.

UP requires: shift above shift_min_pct (15 points); a full recent window; enough baseline days; and every day of the recent window above base_med + MAX(base_mad_sigma, cpu_min_mad_pct), so one spike cannot trigger it. DOWN is the mirror (informational). All inputs are exposed, and every series has one row even when nothing is flagged, so a poller can read it unconditionally. BUSY_PEAK is excluded because it would duplicate BUSY_PCT.

AWR gaps

After missing snapshots, the next one differences against a much older one and the long interval lands on the day it ends. Both CPU daily views publish max_interval_hours, day_gap and gap_flag ('Y' when any interval of the day exceeds cpu_gap_hours). The day stays in the series for the forecast, but percentile and peak-window figures use only intervals within the limit, and CAPA_ANOM (every mode) and CAPA_CPU_SHIFT neither score a gap day nor use it in a baseline. Hour-grain rule: Anomalies: three baselines.

!

Default 12 hours. gap_flag suppresses anomaly scoring, so a tighter value silences the CPU anomaly layer on sites with wide snapshot intervals.

Fixed-ceiling series

CAPD_SERIES_DAILY is keyed by series and carries (dbid, con_dbid, series, day_dt, value, limit_value, unit, n_samples), plus the coverage, gap and worst-instance columns. CAPF_SERIES_FORECAST applies OLS (DRIFT under slope_method = 2; never Theil–Sen) with the M9.1 bands and the same quality ladder, and adds days_to_limit against the per-series limit_value instead of a global percentage knob. A new series is one more UNION ALL branch.

Flag rule

A point flags HIGH (or LOW) when it is more than mad_k · eff_sigma above (below) the baseline median, with eff_sigma = GREATEST(MAD_σ, floor / mad_k). Floors per unit and grain: abs_floor_bytes (100 MiB/day) for tablespaces, 9 points for a CPU day (mad_k · cpu_min_mad_pct), 15 for a CPU hour (cpu_min_mad_pct_hour; hourly values are noisier), series_floor_count, series_floor_gib, series_floor_iops and series_floor_mbps for the fixed-ceiling series. A flat baseline still flags a real jump, sub-floor wiggles never flag, and |robust_z| > mad_k always means flagged. For tablespaces and host busy% this is the pre-M15 rule.

Gaps

A gap row is never scored or used in a baseline, in any mode. Day grain: the cpu_gap_hours rule and every incomplete day (first day, today, restart day). Hour grain: an interval of zero hours or less (DST change, clock step), or longer than LEAST(cpu_gap_hours, hour_gap_ratio × the usual interval). DB_SIZE_GB also treats a day whose tablespace set changed as a gap (a tablespace appearing or dropping out is membership, not growth).

Which modes alert

Every mode is computed and shown in the report and in CAPR_ANOMALIES. Three bitmask knobs choose which modes raise a CAPR_ALERTS row (1 TRAILING, 2 SAME_DOW, 4 HOUR_OF_WEEK). Defaults: alert_modes_tbspc = 1, alert_modes_cpu = 2 (CPU and DB CPU on SAME_DOW), alert_modes_series = 1. alert_modes_cpu = 6 alerts on both weekly modes; an hour-of-week day then raises one row with its worst hour and the number of hours flagged.

i

Times are database wall clock. AWR records local time; hour buckets use it, and one week back is ts − 7 on that clock, across DST too. Exports label these times with a Z and the dashboards run in UTC, so charts show that clock.

Tablespace overrides

The autoextend maxsize in AWR may exceed real storage (32 GiB maxsize on a 10 GiB filesystem). CAP_TBSPC_OVERRIDE sets the real ceiling or excludes a tablespace (e.g. staging that is meant to fill):

ColumnEffect
limit_bytesReplaces the computed ceiling.
exclude_flag'Y' drops the tablespace from forecasts, anomalies, alerts and reports.

Rows survive @install.sql; only @uninstall.sql removes them.

The integration layer

Monitoring systems and every report driver read the same CAPR_ rows.

CAPR_ALERTS: one row per current issue, with severity (CRIT / WARN / INFO) and sort rank, kind, (dbid, con_dbid) plus the db_pdb label from CAPR_CONTAINER, metric value against threshold, and a message. Kinds: TBSPC_FULL, TBSPC_NEARFULL, TBSPC_ANOM, CPU_SAT, DBCPU_SAT, CPU_HOT, DBCPU_HOT, CPU_ANOM, DBCPU_ANOM, CPU_SHIFT, SERIES_LIMIT, SERIES_NEARLIMIT, SERIES_ANOM, DATA_STALE (no AWR snapshot for stale_hours) and MODEL_HEALTH (failed or stale Tier 2 model). Forecast kinds take severity from CAPR_SEVERITY (shared by the report, the fit feed and the alerts) and need a current series. Each row carries a per-row alert_key and a state_key stable across days (kind, keys, series, mode). Anomaly kinds window on anomaly_report_days (14), separate from the report's presentation knob, carry their baseline_mode, and come from CAPR_ANOMALIES, which alone decides an anomaly's severity, message and whether it alerts. Consecutive flagged days of one series and mode arrive as one episode row (first_day, n_days, max_z); a per-day CPU anomaly inside an active level shift drops to INFO.

Results layer

CAPR_ALERTS is evaluated live and has no history. The optional results layer adds it. cap_results.refresh (by hand or via the disabled-by-default CAP_NIGHTLY_JOB) records a run in CAP_RUN, copies CAPR_FIT into CAP_FIT_HIST, and merges CAPR_ALERTS by state_key into CAP_ALERT_STATE, writing an event per change: NEW, ESCALATED, DEESCALATED, RESOLVED (after resolve_grace_runs runs without it) and REOPENED. A failed run is recorded FAILED and re-raised.

CAPR_ALERTS_LATEST: open, unacked states as of the last run (faster than the live view). An ack lasts until its date, or until the alert resolves when the date is NULL; an escalation or reopen clears it. CAPR_ALERT_EVENTS is the change feed (WHERE run_id > :last). CAPR_WEEKLY_DIGEST compares the latest run with the one digest_days (7) earlier: days to full then and now, alerts opened or resolved. CAPR_FORECAST_ACCURACY compares each stored fit's projection with what happened. CAPR_RUNS lists the runs and how fresh the last one is, CAPR_COVERAGE what the suite can see per database, and CAPR_FIT_HISTORY the stored fits of the OK runs. Every report driver can read the last run instead of the live views (SNAPSHOT argument): cap_results.refresh keeps each view the drivers read as a <view>_S table, so a SNAPSHOT report evaluates no view over the AWR data. Two engines

Tier 1 · always on

Pure SQL linear trend

Linear regression, or Theil–Sen when selected. Forecast = slope × days + start; bands from the fit's residuals; anomalies explained by median and MAD. Nothing trained.

Reaches: +30 / +90 (tablespaces also +180 / +365), with 95% bands Needs: nothing beyond the views
Tier 2 · optional

OML ESM (exponential smoothing)

One model per eligible tablespace (top 20 by days to full) and per CPU series (host BUSY_PCT, each container's DB_CPU_SEC) via DBMS_DATA_MINING; the fixed-ceiling series are Tier 1 only. CPU uses additive Winters (weekly seasonality); tablespaces default to AUTO (backtest picks Holt or additive Winters per series). Compared with Tier 1 in report section 6, scored in 6c.

Reaches: its furthest step, at most +30 (19c caps the horizon at 30 steps; 90 days of history give 22) Needs: CREATE MINING MODEL
!

30-step cap. Oracle 19c rejects EXSM_PREDICTION_STEP above 30 at any series length (30 valid, 31 fails at 121/300/600 rows); the package also caps it at a quarter of the series length. CAPF_COMPARE puts the model's furthest step (esm_horizon_days) in the +30 bucket and drops it once the model is older than esm_max_age_days (7); +90/+180/+365 are Tier 1 only. A failed build keeps the previous model and is reported (MODEL_HEALTH). The optional nightly job retrains every night, before its refresh.

A model is built only for series graded OK or LOW_CONFIDENCE, so a flat or static tablespace gets none.
