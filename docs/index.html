AWR Capacity Forecast

Forecasts database capacity and flags anomalies from the AWR history Oracle already keeps. Forecasts use SQL regression and the exponential smoothing models of Oracle Machine Learning (DBMS_DATA_MINING), which ship with the database. Anomalies are days or hours that stand out from a median baseline. It all runs as views and PL/SQL inside the database, with no agent or external ML service.

See a sample report ↗ Get started → Sample: the HTML report run on a fictional database with 150 days of test AWR history.

Output is a set of CAPR_ views, read by SQL*Plus reports (text, HTML, CSV) and, optionally, Kibana, Grafana or an APEX app.

What it computes

Per tablespace, per container and per series.

Data flow

All analytics read CAPV_ views shaped like the AWR dictionary; only that layer touches DBA_HIST_*. One install file maps it to local AWR, a fleet warehouse or test fixtures. Layers: CAPV_ (source) → CAPD_ (daily) → CAPF_ (forecast) / CAPA_ (anomaly) → CAPR_ (report). See How it works.

Forecast engines

Tier 1 · always on

SQL trend line

Linear regression (REGR_*), Theil–Sen or median drift. A forecast is slope × days from today's value; anomalies come with their median and MAD. No training.

Reaches: +30 / +90 / +180 / +365 days, with bands Needs: nothing beyond the views
Tier 2 · optional

OML exponential smoothing

One Oracle Machine Learning ESM model per series, via DBMS_DATA_MINING. CPU uses additive Winters; tablespaces default to AUTO (Holt or additive Winters, chosen by holdout accuracy). The report shows it next to Tier 1.

Reaches: at most +30 days (19c caps ESM at 30 steps) Needs: CREATE MINING MODEL

Space

Measured on the demo schema (150 days of history, 27 trained models, one refresh run): 4.4 MB in total, of which 3.4 MB is the OML models (about 0.13 MB each) and under 1 MB is the suite's own tables and indexes.

  • CAP_FIT_HIST gains one row (about 200 bytes) per series per refresh run; CAP_RUN one row per run; CAP_ALERT_EVENT one row per alert state change. A daily refresh on 25 series adds roughly 2 MB per year.
  • Nothing is purged automatically. cap_results.purge(p_keep_days => 400) deletes older results.
  • create_owner.sql sets a 1 GB quota by default (owner_quota).

Privileges

create_owner.sql (run once as SYSDBA) creates a dedicated owner, C##AWRCAP in CDB$ROOT or AWRCAP in a PDB, and grants only the following. Grants are direct because views and definer's-rights packages ignore roles.

In CDB$ROOT the grants are CONTAINER=ALL. No ANY privileges, no DBA role, no ALTER SYSTEM. CAP_REPORT_SPOOL_JOB needs a directory object, which a DBA creates separately.

Reads, writes and load

  • Reads only the DBA_HIST_* views above. It does not change AWR settings, snapshot interval or retention.
  • Writes only its own seven tables (and OML model tables). No DML or DDL on any other schema.
  • Load happens only when a report, cap_results.refresh or a training call runs: queries over AWR history, and for Tier 2 one ESM build per series. Nothing runs in the background unless you enable the jobs.
  • Licensing: DBA_HIST_* requires the Diagnostics Pack (doctor.sql checks CONTROL_MANAGEMENT_PACK_ACCESS). Oracle Machine Learning has been included with the database license since December 2019.

Re-running @install.sql keeps the seven tables and the models. @uninstall.sql drops every object, the models and the jobs.
