Verified on 19c

Caveats

Verified on 19.27.

!

AWR retention bounds everything. Default is 8 days; the 90-day training window needs more. Short retention gives INSUFFICIENT_HISTORY.

i

Block size comes from DBA_HIST_TABLESPACE, not the datafile view: DBA_HIST_DATAFILE has no SYSTEM row on stock 19c, which would drop that tablespace.

i

REGR_R2 returns 1 for a flat series, not NULL (NULL only when x variance is zero). So FLAT is detected by slope = 0.

!

ESM is capped at +30 days on 19c. The horizon hard-caps at 30 steps regardless of series length, and the package also caps it at a quarter of the series length (90 days of history give 22 steps). CAPF_COMPARE shows the model's furthest step while the model is at most esm_max_age_days old; +90/+180/+365 are always REGR-only.

i

Anomalies key off the growth rate, not the raw delta. Across an AWR gap, the delta is divided by day_gap, so a multi-day gap is never mistaken for a one-day spike.

i

Container identity is the composite key. Analytics key on (dbid, con_dbid); con_dbid separates PDBs whose TS# collide. Cross-DBID series stitching is a v2 item, as is memory (SGA / PGA) forecasting.

▸

Re-install is non-destructive. CAP_CONFIG knobs, CAP_TBSPC_OVERRIDE and CAP_TBSPC_FAMILY rows, CAP_ML_MODEL registry and the results layer's run history, alert state and acks survive @install.sql. Use @uninstall.sql for a full teardown.

Tuning

Configuration knobs

Thresholds live in CAP_CONFIG. Views read it only through the one-row view CAP_CFG (one column per knob, named after the knob). The table lists every knob the ddl/05_config.sql seed inserts (one row per knob, plus suite_version) with its shipped default; test/docs_lint.sh fails when one is missing.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 0.70 WHERE cfg_name = 'r2_gate';
SQL> SELECT * FROM cap_config ORDER BY cfg_name;   -- the full annotated list
SQL> SELECT * FROM cap_cfg_check WHERE status <> 'OK';   -- missing or out-of-range knobs
SQL> UPDATE cap_config SET cfg_value = cfg_default WHERE cfg_name = 'r2_gate';   -- back to the shipped value
!

Reset a knob, never delete it. A deleted row reads as NULL in CAP_CFG, and a NULL knob makes the views return no rows or no flags, without an error. cfg_default holds the shipped value and is refreshed on every install; UPDATE cap_config SET cfg_value = cfg_default is the reset. @install.sql never touches cfg_value and re-inserts a deleted key with its shipped value. Where cfg_value differs from cfg_default, the knob has been tuned.

CAP_CFG_CHECK returns one row per knob with its value and a status: OK, MISSING (no CAP_CONFIG row) or BAD (a broken rule: recent_days ≤ train_days, min_train_days ≥ 14, dtf_crit ≤ dtf_warn, quiet_ratio2STOP / START: the pause must also be at least this many times the longest other pause in the window (STOP: the pauses between two growth days; START: those and the pause up to the newest day). A tablespace that grows in rare steps keeps its whole window.

growth_floor0.001STOP / START: a day is a growth day when used_bytes is above every earlier day of the window by more than this fraction of the window's rise (maximum − minimum).

Before you start

Memory (PGA)

Installing is cheap. Running is not: every session that evaluates the full view chain (cap_results.refresh, each report driver, test/run_test.sql) needs 1.1 to 1.8 GB of PGA. Size pga_aggregate_limit for it before the first report.

!

Sizing rule. pga_aggregate_limit ≥ the background PGA of the idle instance (total PGA allocated in V$PGASTAT, about 0.5 GB on the 19c test box) + 1.5 GB per suite session that can run at the same time (2 GB per concurrent run_test.sql). The host needs that much free RAM on top of the SGA. On 19c the default limit is the largest of 2 GB, twice pga_aggregate_target and 3 MB × PROCESSES. On a small instance that is 2 GB: room for one suite session and nothing else.

Every figure below is one SQL*Plus session's session pga memory max, measured with test/pga_probe.sql at the end of that session. Test box: Oracle 19.27, 2 vCPU, 7 GB VM, SGA 1.5 GB, pga_aggregate_target 512 MB, pga_aggregate_limit 5 GB, nothing else running.

Why pga_aggregate_target does not cap it. Almost none of that memory is sort or hash work area: the largest single work area needs under 8 MB. It is the memory Oracle uses to parse and run the deep CAPV_ → CAPR_ view stack (EXPLAIN PLAN of CAPR_ALERTS alone takes about 200 MB), and the session keeps it until it disconnects. It follows the number and depth of the statements a session runs more than the data volume: the small fixture peaks higher than 35 days of real AWR, because run_test.sql runs far more distinct statements in one session. pga_aggregate_target only steers work areas; pga_aggregate_limit is the ceiling that applies.

What happens when the limit is too low. When the instance goes over pga_aggregate_limit, sessions wait on acknowledge over PGA limit. Oracle then terminates the largest ones with ORA-04036. On a 4 GB test VM with a 2 GB limit, two harness runs at once stalled for over an hour in CAPR_ALERTS. With 7 GB of RAM and a 5 GB limit, the same work finishes in the times above.

A small pga_aggregate_target costs TEMP, not failures. With a 512 MB target and about 500 MB of background PGA, the automatic work-area target drops to 0–32 MB. Work areas then spill: one run_test.sql run writes about 2.2 GB to TEMP in small one-pass sorts. A target of 1 GB or more keeps them in memory.

Scheduler jobs. install_jobs.sql runs the night's work as one job, CAP_NIGHTLY_JOB at 01:00. Its steps run one after the other in one session, so the night never needs two suite sessions' PGA at once, however long a step takes. On a repository each step grows with the number of targets (How many targets). A report you run by hand while the job runs needs a second session's worth. CAP_COLLECT_JOB (repository mode, hourly) runs beside the nightly job. It copies rows without reading the view stack, and its PGA has not been measured.

Measure your own. At the end of any SQL*Plus session that did the work, run @test/pga_probe.sql. It is read-only and needs SELECT on the V$ views it names (SYSDBA or SELECT_CATALOG_ROLE). It prints the session's peak PGA and UGA, how its work areas ran (optimal, one-pass, multi-pass), the TEMP it wrote, the ten largest work areas of the current schema's cursors and the instance PGA counters.

How a collect copies. cap_repo.collect works per DBID, in chunks of 500 snapshots. A chunk appends the fact views' rows above the DBID's high-water mark, merges the dimension views (tablespaces, datafiles, containers, instances, ASM diskgroups, segment names) and moves the mark, in one transaction. A failure keeps the previous boundary, so the next collect repeats only the failed chunk. The DBID row is locked for the chunk, so two collects never copy the same window twice. A failing target is logged and the others go on; the call then raises ORA-20070 with the number that failed. The first collect of a DBID copies every snapshot the target still holds. On RAC an instance can finish a snapshot before another, and facts are copied once, so a collect holds back the newest snapshot while fewer instances have it than the one before; the next collect copies it (named in the output and in CAP_COLLECT_LOG). A single instance never waits. RAC is untested.

Optional sources. CAP_REPO_SOURCE.optional marks a view a target's reader may not be able to read yet: DBA_HIST_PGASTAT and the memory sizing sources (DBA_HIST_MEM_DYNAMIC_COMP, DBA_HIST_SQL_WORKAREA_HSTGRM, the PGA, SGA, buffer cache and shared pool advisors, DBA_HIST_SGASTAT, DBA_HIST_LIBRARYCACHE, DBA_HIST_ROWCACHE_SUMMARY, DBA_HIST_SYSTEM_EVENT), which a target prepared before M26 has no grant on. add_target and cap_repo.ping warn about it instead of failing; collect skips its pull on ORA-00942 or ORA-01031, copies everything else, moves the high-water mark as usual, prints one [WARN] line per target and names the views in the OK row of CAP_COLLECT_LOG. The memory verdicts of that target read INSUFFICIENT_EVIDENCE / NOT_COLLECTED, and doctor.sql check 11 says to re-run target/prepare.sql. The copy starts at the next collect after the grant; nothing is backfilled.

!

Collect before the target forgets. A target keeps its own AWR retention (8 days on a stock database). If the repository stops collecting for longer than that, the snapshots in between are gone: the next collect copies what is left and logs a GAP. A DBID already registered to another target is refused and logged as COLLISION, which happens when a clone was restored without a new DBID.

Space. On the 19c test CDB (three containers, about 40 snapshots a day) the copies hold 1.9 MB of rows for 7.5 days, about 0.25 MB a day, most of it segment statistics. At the default 400 days that is about 100 MB of rows per target, before block overhead. It grows with snapshots per day, containers and busy segments.

The scheduler clears the job's CLIENT_IDENTIFIER between runs.

CLIENT_INFO carries a report's scope. A report driver run for one dbid or target sets AWRCAP dbid=<n> for the length of the run, so V$SESSION.CLIENT_INFO shows which database a running report reads (Report drivers). The suite sets it nowhere else.

On a target the label goes over the link through DBMS_APPLICATION_INFO, which the reader can execute through the stock PUBLIC grant. A target that revoked that grant shows the session unlabelled; collection is not affected. APEX labels its own sessions (APEX:APP …). The ORDS handlers are not labelled by the suite.

Re-running it · upgrading

Re-install and upgrade

Re-running @install.sql keeps every persisted table: CAP_CONFIG, CAP_TBSPC_OVERRIDE, CAP_TBSPC_FAMILY, CAP_DISK_OVERRIDE, CAP_ML_MODEL (with its OML models), the results layer (CAP_RUN, CAP_FIT_HIST, CAP_ALERT_STATE with acks, CAP_ALERT_EVENT) and, in repository mode, the target registry, the collect log and the CAP_H_* copies. 00_drop skips them; the config MERGE inserts missing keys and on existing keys refreshes only cfg_default and cfg_desc. Exception: suite_version, overwritten on every install so doctor.sql shows which release built the objects.

Upgrade: pull the new revision and re-run @install.sql with the same deploy_mode. Views are CREATE OR REPLACE; persisted tables are created only if absent and new columns are added in place; new knobs are MERGE-seeded with their shipped default. Run @doctor.sql afterwards to confirm nothing is INVALID. A release that reads a new statistic copies it from the first collect after the upgrade: collect starts above the high-water mark, so older snapshots are not backfilled. The I/O series IOPS and IO_MBPS (M27) therefore start on the day of that collect for every target, and read INSUFFICIENT_HISTORY until min_train_days days have passed. Until those older snapshots leave the target's AWR, test/dbmint_copy_check.sh reports their I/O rows as missing from the copy. @uninstall.sql removes the scheduler jobs, views, types, packages, OML models, a repository's database links and every persisted table; it prints any error other than "does not exist" and ends with the number of CAP% objects left (0 expected). Before it drops anything it writes the knobs off their default and the CAP_TBSPC_OVERRIDE, CAP_TBSPC_FAMILY and CAP_DISK_OVERRIDE rows to reports/cap_config_replay_<schema>_<timestamp>.sql and prints the path; run that file in the new owner after the next install. A knob the new release no longer has is named and skipped. With nothing to replay it writes no file.

From local mode (before M25). A local install read its own DBA_HIST_* in CDB$ROOT; that mode is retired and install.sql refuses it. Move such an install in four steps:

  1. @uninstall.sql in its schema, as SYSDBA. It writes the replay file and revokes the owner's old DBA_HIST_* grants and CONTAINER_DATA.
  2. ./quickstart.sh or ./install.sh --profile standalone: the database as its own target, the suite in a PDB owner.
  3. The replay file, in the new owner.
  4. EXEC cap_repo.collect (the standalone run has done the first one).

The first collect copies everything the AWR still holds, so the forecasts come back at once. What does not move: the run history (CAP_RUN, CAP_FIT_HIST), the alert states with their acks and CAP_ALERT_EVENT, and the OML models (retrain).

AWR retention

!

Default retention is 8 days, below the 90-day training window, so the first collect from a stock database copies 8 days and its forecasts start INSUFFICIENT_HISTORY (TRAIN_N < min_train_days). The copies then grow with every collect, up to repo_retention_days, while the target keeps its own retention. target/check.sql reports the retention, doctor.sql check 7 the days the copies hold.

To start with more history, raise retention on the target (90 days, in minutes):
