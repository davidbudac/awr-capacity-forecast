Testing

Track A: fixture data with closed-form answers. Track B: the same code against live AWR. Track C (optional): a swingbench workload that generates AWR history. The two no-install queries under standalone/ have their own lever.

Before you start

Track A

Fixture self-check

Install fixture mode as CAPTEST in PDB1, then run the Tier 1 and Tier 2 (ESM) self-check scripts. Each assertion is compared against a closed-form answer; each script prints its own count. No AWR history needed.

Where: PDB1 · captest/<password> Proves: forecasts, intervals, robust slope, resets, overrides, CPU peaks/gaps/shifts, fixed-ceiling series, alerts, ESM Time: ~30 minutes
Track B

Standalone smoke on cdb1

Run quickstart.sh as sysdba in CDB$ROOT: the database becomes its own target, the suite lands in a PDB owner and copies the CDB's AWR over a loopback link, then the report runs. On a stock box expect INSUFFICIENT_HISTORY until the copies grow.

Where: cdb1 · / as sysdba · CDB$ROOT, suite in PDB1 Proves: it runs end-to-end on your AWR Time: a few minutes (+ the history wait)

What the fixture contains

test/fixture_install.sql has no randomness. Every series is a closed form anchored to TRUNC(SYSDATE) (the training windows use SYSDATE); expected answers are stored in CAP_FIXTURE_META. The fixture enters through its own seam (ddl/12_seam_fixture.sql), so every view above it is the code a repository runs: Architecture · The seam.

The snapshot spine

121 day indices i = 0..120, based at TRUNC(SYSDATE) − 120, with two snapshots a day under the fake dbid/con_dbid 42424242 (cannot collide with real AWR):

Two deliberate holes:

  • Restart day (i = 60): no 06:00 snapshot. The 18:00 snapshot has a new startup_time and reset counters, so its interval spans the restart and the startup-time guard drops it. The day is absent from the CPU series, REDO_GB_DAY, IOPS and IO_MBPS.
  • CPU gap day (latest Sunday in i = 70..80): both snapshots exist but carry no OSSTAT / time-model rows. The next 06:00 interval differences against 18:00 of the day before and spans 36 h.

▸

Gap day: guard test. The day after the Sunday gap has one 36 h interval plus the normal 12 h daytime one: 30% busy against a 40% Monday baseline, past the 9-point threshold. It is not flagged because gap_flag = 'Y' suppresses scoring. busy_p95 reads 60, from the 12 h interval alone: the 36 h interval (20%) is excluded from p95/max as too long. Unfiltered p95 of {20, 60} would be 58.

▸

FIXPDB1 level shift (DB_CPU_PCT). Any 7 consecutive sawtooth days contain each offset once, so both medians are exact: base_med = 40 over the 28-day baseline, recent_med = 58 over the last 7, shift_pct = 18, base_mad_sigma = 4 × 1.4826 = 5.93 for the N-of-M confirmation. Each step day is 18 points over its same-weekday priors: SAME_DOW flags all 7 (floored sigma, threshold 9, z 6) and DBCPU_ANOM raises one episode row for the 7 days, INFO because the level shift is active (CPU_SHIFT is the WARN); TRAILING, whose window mixes in the sawtooth, flags 3. Once the step fills the baselines the flags stop and the trend fit reads it as noise; CAPA_CPU_SHIFT still reports it.

▸

Inverted Wednesday. Both intervals read 40%, a normal weekday average, so TRAILING and SAME_DOW do not flag it. HOUR_OF_WEEK flags 06:00 HIGH (40 vs 20, z = 20 / 5 = 4) and 18:00 LOW (40 vs 60). Injected Tuesday: 06:00 reads 70 vs 20 (z 10) and flags; 18:00 reads 70 vs 60, under the 15-point hour threshold, and does not.

!

The injected Tuesday is also a FIXPDB1 step day. It is the latest Tuesday in the spine, so inside the last 7 days, where FIXPDB1's DB_CPU_PCT is also scored. A CPU anomaly lookup by day alone returns several rows; every lookup in run_test.sql names series, baseline mode and con_dbid (helpers anom_flag, anom_n).

Every counter reads k × its increment. On the k-th snapshot of a startup each counter and advisor estimate reads k times its increment, so it drops at both restarts (the partial day's noon restart and day 60) and every ratio is the ratio of the increments. MEM_U = ROUND(window DB time / 6000) seconds: an increment of a × u an interval is a percent of DB time. over allocation count has no row until its first use in a startup, and free buffer waits first appears at day 100 06:00, where its first row counts in full.

Steps 1 to 6 on dbmint in one script. test/dbmint_harness.sh <SCHEMA> [--ml] [--no-fixture] [--pga] [--parity] [--sql FILE] runs test/check.sh (below) first and stops on a failure (exit 4), rsyncs the checkout to ~/awr_cap_<schema>/, runs the fixture install, the install, run_test.sql and, with --ml, the Tier 2 steps as SYSDBA with CURRENT_SCHEMA set in PDB1, and echoes the RESULT, FAIL and ORA- lines. Log: /tmp/dbmint_harness_<SCHEMA>.log. One schema per concurrent run: two runs reinstalling one schema fail with ORA-04063 or ORA-00942. The lever refuses a start (exit 3) while the schema has a run. --pga ends every step with test/pga_probe.sql, which logs that session's peak PGA and largest work areas (see Memory (PGA)). --sql test/mem_timing.sql times one read of each memory verdict view, to compare before and after a change to ddl/42_memory_views.sql.

The run is detached. The steps run on dbmint under setsid and nohup, from ~/awr_cap_<schema>.harness/run.sh. Beside it are harness.log, state (pid, start time, git SHA, step list, then exit status and end time) and lock, which the run and its SQL*Plus sessions hold. The workstation only follows the log into /tmp/dbmint_harness_<SCHEMA>.log. When the lever is killed or the connection drops, the run finishes on dbmint. --attach starts nothing: it follows the schema's run to its end, or prints the result of the last finished one, and exits with that run's status (5 when there is none). --status prints one line: running since, finished with exit N, or none. The state keeps the last run only. With --parity the parity run is the last step of the detached run.

Partial runs and queueing. --ml-only takes the schema as it is: no fixture load, no install, no run_test.sql, only cap_forecast_ml.train_all and run_test_ml.sql. --sql-only runs only the --sql FILE scripts. --wait-slot [N] waits before the start while N (default 2) or more SQL*Plus processes or harness runs are active on dbmint, polling every 15 seconds. The fixture is anchored to its load day, so run_test.sql fails date assertions when a run crosses the VM's midnight, or when a partial run uses a fixture loaded the day before. The lever prints a warning when the VM clock is within 100 minutes of midnight.

quickstart.sh runs, in one SQL*Plus session: target/self.sql (the reader with a random password, then target/check.sql: container, the reader's grants and CONTAINER_DATA, Diagnostics Pack, STATISTICS_LEVEL, AWR retention and interval, the newest snapshot), create_owner.sql in the PDB, repository/self.sql (on a re-run it re-points the link at the new reader password; before the first install it does nothing), doctor.sql (the owner's privileges and a readiness table of days needed versus days available per feature; a FAIL stops before install), install.sql (deploy_mode = repository), repository/self.sql (registers the database as target CDB1 and copies its AWR) and the text report. 3

Prove the copies

test/dbmint_copy_check.sh <SCHEMA> [TARGET] [--collect] [--plant SOURCE] runs test/repo_copy_check.sql, which repository/build.py generates from its manifest. Per target, DBID and source it compares the source over the link, under the manifest's row filter, with the copy both ways: facts over the collected snapshot window, dimensions whole, segment names over the segment statistics' keys. A dimension row the copy keeps after the target purged it is listed as kept, not as a difference. It runs in a throwaway definer's-rights procedure in the repository schema, because a private link resolves only for its owner. Exit 0 when every copy equals its source, 1 on a difference, 5 when a snapshot landed during the check (rerun). --plant OSSTAT deletes one copy row uncommitted and passes only when exactly that row is reported. Equal copies under the same seam text give the same views.

Outside the suite

The standalone queries

standalone/tbspc_capacity.sql and standalone/tbspc_monitor.sql install nothing and read AWR directly, so the fixture harness does not reach them. test/standalone_test.sh <SCHEMA> [--no-fixture] tests them against designed series, in under a minute. Log: /tmp/standalone_test_<SCHEMA>.log.

workstation · bashyou run
test/standalone_test.sh CAPS1
  • How the unchanged files get test data. Both files name their sources without a schema. test/standalone_fixture.sql creates views named like them (DBA_HIST_SNAPSHOT, DBA_HIST_TBSPC_SPACE_USAGE, CDB_TABLESPACE_USAGE_METRICS and four more) in a throwaway schema. Under ALTER SESSION SET CURRENT_SCHEMA the queries read those instead of the real AWR. The script refuses an Oracle-maintained schema.
  • The shipped text runs. The lever cuts each file's SELECT out of the file and puts CREATE OR REPLACE VIEW in front of it. Three more views carry one edited setting each (quiet_days 0, disk_free_gb set, alerts_only 0). At the end both files also run as they are, with @file.
  • Today is a setting. The queries take today from the newest snapshot. The one-row table SA_CTX holds a world and a day index, and the views show the snapshots up to that day. So one series is judged on many days, for example a month's tablespace on every day from the day its growth stopped until its last growth day has left the 90-day window.
  • Three worlds. W1 holds the growth shapes: a steady grower, a month that fills and stops, one bulk load, two growth days, rare steps, a weekly batch, a purge, a sawtooth, the status thresholds and what must not be listed. W2 holds four tablespaces on one shared disk. W3 holds one tablespace per branch of the monitoring rule.
  • Closed forms. test/standalone_test.sql asserts restart, fit window, growth per day, quality, days to full, the shared-disk columns, status and alert from the series as designed. It prints PASS or FAIL per check and a RESULT: line, and exits non-zero on a failure.
  • One forecast in two files. Before it syncs, the lever compares the CTE chain db to res of the two files and stops when they differ in more than the monitor's live_pct lines.
Track C, optional

Workload (bench/)

bench/ is a swingbench harness that generates shaped daily load, so an idle test instance gets AWR history. The suite does not depend on it; install.sql installs nothing from it.

LoadPurpose
SOE (Order Entry) OLTP insertsgrow SOETBS monotonically, for CAPF_TBSPC_FORECAST / days-to-full
SH (Sales History) rollups and cubesCPU with almost no growth, so CPU and tablespace series move independently
Weekday / weekend contrastseasonal signal for dow_weeks (SAME_DOW and HOUR_OF_WEEK baselines)
anomaly_load.sql + a 24-user burstan outlier for CAPA_ANOM

Six daily phases: ramp (4 SOE users, 45 min), peak (16 users, 60 min, CPU near cpu_sat_pct), dss (3 SH users, 30 min), mixed (8 SOE + 2 SH, 45 min), batch (6 users, 20 min, redo/undo heavy) and anomaly (24 users, 30 min). run_phase.sh forces an AWR snapshot before and after each phase. At weekends weekday-only phases skip and the others halve their user count.

workstation · bashyou run
cp bench/env.sh.example bench/env.sh && $EDITOR bench/env.sh   # once; the only place credentials live

./bench/setup/setup.sh                # AWR settings + tablespaces + both schemas
./bench/run_day.sh --short            # ~50 min smoke run
./bench/run_phase.sh peak             # a single phase
crontab bench/cron/bench.crontab      # daily shape from here on

./bench/teardown.sh                   # drop it all, restore the AWR settings
!

It changes AWR settings and creates schemas. bench/setup/01_awr_settings.sql switches the CDB to 15-minute snapshots with 35-day retention, and 02_bench_objects.sql creates SOETBS / SHTBS (capped autoextend) plus a PDB-local wizard DBA. Test boxes only; teardown.sh reverses it.
