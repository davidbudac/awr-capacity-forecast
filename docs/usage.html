Guide

Usage

Run and read the report, drill into a series, poll the alert views, set overrides and tune CAP_CONFIG. Nothing here writes to AWR.

Generate

Run the report

SQL*Plusyou run
sqlplus / as sysdba              -- or connect as the suite owner
SQL> ALTER SESSION SET CONTAINER = PDB1;
SQL> ALTER SESSION SET CURRENT_SCHEMA = AWRCAP;   -- where the suite lives
SQL> @report/report.sql               -- everything from report/defaults.sql
SQL> @report/report.sql 5             -- top_n=5, the rest defaulted
SQL> @report/report.sql 5 7 N         -- top_n / anomaly_days / show_esm
SQL> @report/report.sql 10 30 AUTO 42424242 42424243   -- one container only
SQL> @report/report.sql - - - - - SNAPSHOT             -- from the last refresh run

Run it from the repo root: on 19c SQL*Plus resolves @@ includes relative to the outermost caller. It loads report/defaults.sql, so a bare run never prompts, and spools to reports/cap_report_<db>_<ts>.txt. It only SELECTs and creates or modifies no object. Identity comes from SYS_CONTEXT, so no V$ or catalog privileges are needed.

Positional arguments: [top_n] [anomaly_days] [show_esm] [dbid] [con_dbid] [source]; - skips one
PositionNameDefaultDoes
1top_n10Rows in the days-to-full, near-full, forecast and ESM-compare rankings.
2anomaly_days30Trailing days of anomalies printed in sections 3 and 5. Presentation only; CAPR_ALERTS uses the anomaly_report_days knob (14).
3show_esmAUTOAUTO = section 6 only if OK models exist, else a one-line hint; Y = always; N = skip. Case-insensitive.
4dbideveryOnly this database in every section; top_n ranks inside it.
5con_dbideveryOnly this container (pass - for the dbid to scope on the container alone).
6sourceLIVELIVE evaluates the views now. SNAPSHOT: every section from the newest refresh run of the results layer, read from the <view>_S tables cap_results.refresh fills, and the alert list from CAPR_ALERTS_LATEST (lifecycle and acks). No view over the AWR data is evaluated: seconds and little PGA. The header names the run; before the first refresh after an install it says so and the sections are empty.
▸

Defaults. report/defaults.sql holds the defaults both drivers load. Positional arguments override them for one run; an omitted argument falls back to the file. Neither form prompts. Both scripts UNDEFINE their arguments at the end, so a later argument-less call in the same session does not inherit them. Analytics thresholds are in Configuration.

CSV and cron

@report/report_csv.sql [dbid] [con_dbid] [source] writes one CSV per CAPR section view (alerts, days to full, forecast, anomalies, CPU trend and shifts, series, fit, and the four memory views: verdicts, evidence, components and component points) into reports/cap_csv_<db>_<ts>/: every column and row in scope, a header line, every value quoted. report/run_report.sh [connect] [--html] [--csv] [--scope D[:C]] [--target NAME] [--snapshot] [--keep N] [--container PDB] [--schema OWNER] runs the drivers from the repo root (--target scopes them to one target by name, its dbid with the newest snapshot), prints each file it wrote, and exits non-zero when sqlplus exits non-zero (a failed --container / --schema aborts the run), when the session output has an ORA- or SP2- line, or when a spool is missing or contains one.

crontabdaily 06:30
30 6 * * * . ~/.bash_profile; /opt/awrcap/report/run_report.sh "/ as sysdba" --container PDB1 --schema AWRCAP --html --keep 14 >> /var/log/awrcap_report.log 2>&1
Generate · alternative

HTML report

SQL*Plusyou run
sqlplus / as sysdba              -- run from the repo root, in the suite owner as above
SQL> @report/report_html.sql        -- spools reports/cap_report_<db>_<ts>.html
SQL> @report/report_html.sql 25 60 Y  -- same three positional arguments

A single self-contained page. Same defaults file, knobs and read-only behaviour as the text report. One section per metric: tablespaces, database size, host CPU, DB CPU, sessions, processes, PGA, redo, undo, temp and ASM disk groups, then memory. Each series is a card with status, current value, share of the limit, growth, days to the limit, and a chart (drawn for every series): history, the dashed forecast with its 95% band, the limit and its warning line, a “today” divider, rings on anomalous days, the ESM point, and a dot where the forecast crosses the line the days figure counts to. CPU cards add a 14-day by 24-hour heat strip with flagged hours outlined.

The page opens with the alert counts, one index row per metric (status, headline, sparkline, date its soonest limit is reached) and the CAPR_ALERTS list, each row linking to its card. Hovering a chart shows that day's value. Past top_n series in one metric, the rest are compact rows with a sparkline. The SQL writes the rows of CAPR_FIT, CAPR_SERIES_POINTS, CAPR_FORECAST_POINTS, CAPR_ANOMALIES, CAPR_ALERTS and CAPR_HOURLY_POINTS into the page as JSON; a script in the page draws them. No library, no external assets, works offline, needs JavaScript. A view that fails leaves its block empty and the page names it. Sample report.

The Memory section has one card per instance: the six sizing verdicts of section 8 (grade, current size, suggested size and its parameter, the verdict sentence and its reason), the evidence of each area behind a fold, and a chart of the SGA component sizes per day of the evidence window with a table of each component's size, share and resizes. Its rows come from CAPR_MEM_VERDICT, CAPR_MEM_EVIDENCE and CAPR_MEM_COMP_POINTS. The verdicts are advice: they are not counted in the alert totals or the banner.

report/report_brief.sql is a one-page briefing: one sentence (what fills, when, how much to add), a 12-month timeline of the date each limit is reached, the actions in date order with worst-case dates, the memory sizing advice (one line per verdict that advises a change, and a count of the areas that could not be judged), the evidence chart for the first few, and one fill bar per tablespace for today and +90 days. Same arguments, read-only, printable; run_report.sh --brief writes it from cron. Sample briefing.

i

Same rows. Both drivers read the CAPR_ per-section views, where every derived number, label, severity marker and unit conversion is computed; the HTML driver reads the point-feed views built on them and only lays out rows. The text and HTML reports show the same numbers.

Interpret

Reading the report

Sections 0–8 and the views behind each
#SectionWhat to read
0At a glance
CAPR_ALERTS		 CRIT / WARN / INFO counts, then one line per current issue: severity, kind, DB/PDB, message. The HTML banner and external pollers read the same view. Anomaly kinds use the anomaly_report_days knob, not anomaly_days. The header prints the data-through date, the last refresh run and the coverage line (CAPR_COVERAGE); a DATA_STALE row comes first. With SNAPSHOT the list is the open, unacked states of the last refresh run.
1Days-to-full & near-full
CAPR_TBSPC_DAYS_TO_FULL		 1a ranks tablespaces by days_to_full at any fit quality; QUALITY says how far to trust it. CRIT at/below dtf_crit days, WARN at/below dtf_warn; ACCEL > 1.5 = accelerating growth. WORST/BEST bound the estimate with the 95% slope CI (empty BEST = might never fill). 1b ranks by PCT_USED alone, independent of fit quality. GATE says why a row inside the warning window does not page (low-q, cyclic, stale), so SEV matches CAPR_ALERTS. NEED_90_GIB: space to add so the upper 95% band stays under the ceiling for 90 days; ADD_BY: worst-case fill date. A CYCLIC tablespace is ranked on its peak line.
2Tablespace forecast
CAPR_TBSPC_FORECAST		 Current / +30 / +90 / +180 GiB with TRAIN_N, R², quality, and ESM columns when Tier 2 models exist: ESM_GIB is ESM_H days after the last day (the model's furthest step, at most 30, minus its age). 180_LO/180_HI: the 95% prediction band at +180. A tablespace prints only if growing, near-full, or at least report_min_gb GiB used, capped at top_n; the header states how many of the total it shows.
3Tablespace anomalies
CAPR_TBSPC_ANOMALIES		 Flagged days inside anomaly_days, one line per (day, baseline mode): growth rate (delta ÷ gap), baseline median rate, threshold max(k·MAD, 100 MiB/day floor), robust z and N_HIST (baseline days). MODE: TRL (last mad_window_days) or DOW (same weekday over dow_weeks); a day can flag under one and not the other. GAP is days since the previous sample (> 1 across an AWR gap), which is why the rate, not the raw delta, is scored.
4CPU trend
CAPR_CPU_TREND		 Six metrics per container: BUSY_PCT (daily average), BUSY_P95 (p95 of the day's intervals), BUSY_PEAK (the peak_hour_from/peak_hour_to window), and DB_CPU_SEC, DB_CPU_PCT, DB_CPU_P95: this container's DB CPU as a share of the host's logical CPUs (NUM_CPUS, capped by cpu_count). DAYS_SAT projects when the metric reaches cpu_sat_pct (not for DB_CPU_SEC, which has no percentage ceiling), with WORST/BEST from the slope CI, starting from the anchor (median of the last shift_days complete days). SIG = Y when the slope is outside its 95% CI (the default quality gate). HOT = Y when the recent p95 median is at or above cpu_sat_pct (a CPU_HOT / DBCPU_HOT alert). GATE says why a row does not page.
5CPU anomalies & level shifts
CAPR_CPU_ANOMALIES · CAPR_CPU_SHIFTS		 5a: flagged CPU points, host BUSY_PCT and each container's DB_CPU_PCT (METRIC), against three baselines (MODE): TRL (last 28 days), DOW (same weekday), HOW (same weekday and hour; catches a normal daily average with an inverted profile). WHEN is the day, or day, weekday and hour for a HOW row. Weekly seasonality is handled by the baselines, not modelled. 5b: sustained level shifts. The recent window's median is compared with the preceding baseline median; it flags only when the gap exceeds shift_min_pct points and every recent day sits above (UP) or below (DOWN) the baseline median ± its MAD-sigma. The N-of-M column shows that count.
6ESM compare & backtest
CAPR_ESM_COMPARE · CAPR_BACKTEST		 6a tablespaces and 6b CPU: Tier 2 beside Tier 1 at each horizon with the ESM CI; ESM_MODEL is HOLT or ADDW (EXSM_ADDWINTERS, 7-day season). 6a shows the same tablespaces as section 2 (four horizons each). 6c: the holdout scorecard (Backtest). With show_esm=AUTO and no models the section is a one-line hint.
7Fixed-ceiling series
CAPR_SERIES · CAPR_SERIES_ANOMALIES		 PROCESSES, SESSIONS: peak concurrency (AWR high-water mark since instance startup, summed across RAC instances) against the init parameter. PGA_ALLOC_GB: the day's highest sampled PGA allocation in GiB against pga_aggregate_limit. REDO_GB_DAY: redo per day, no ceiling; a trend for FRA / archive-destination sizing. DB_SIZE_GB: permanent-tablespace bytes used against the summed tablespace ceilings. ASM_DG:+<group>: diskgroup GiB used against its total. TEMP_PEAK:<ts> / UNDO_PEAK:<ts>: the day's highest sampled TEMP / UNDO usage against maxsize. FRA_DAYS on the REDO_GB_DAY row: db_recovery_file_dest_size over the current redo rate. DAYS_LIM projects when the series reaches series_sat_pct% of its limit (default 90, because reaching processes exactly is an outage). 7b (CAPR_SERIES_ANOMALIES): flagged anomalies, one line per (day, mode); PROCESSES, SESSIONS, PGA_ALLOC_GB and REDO_GB_DAY on level, DB_SIZE_GB on daily growth in GiB.
8Instance memory
CAPR_MEM_VERDICT · CAPR_MEM_EVIDENCE · CAPR_MEM_COMPONENTS		 One grade per instance and memory area (SGA total, buffer cache, shared pool, SGA balance, PGA target, PGA limit), judged on the last mem_window_days (30) of AWR. UNDERSIZED: Oracle's advisor estimates a material gain at a larger size and a pressure symptom was observed; either one alone grades OK and the reason says which. OVERSIZED: the advisor estimates almost no cost at a smaller size, no pressure was observed and enough days were sampled. INSUFFICIENT_EVIDENCE: the reason says what is missing (advisor history, AMM, memory history not collected). SGA balance reads THRASHING when ASMM keeps moving memory between the buffer cache and the shared pool, DRIFTING when it squeezed one of them. SUGGESTED is a size the advisor evaluated, at most mem_max_step times (or one over it) the current size: one step, then judge again. Under ASMM a buffer cache or shared pool suggestion is a floor. HOST = Y: the suggestion plus the rest of the instance passes mem_host_ram_pct of the host's memory (other instances on the host are not seen); SGA = Y: a pool floor that does not fit in sga_target. Under the table each verdict is one sentence with its reason. 8b: every signal behind the verdicts, with its value and threshold (ADVISOR, SYMPTOM, USAGE, CONTEXT; PRESSURE / SLACK / NEUTRAL). 8c: the SGA components with their current, smallest and largest size in the window and their resizes. The rows are instance level, so a report scoped to a PDB shows none. Advice only: no alert is raised and the suite never changes a parameter. report/drill_mem.sql shows the arithmetic.
!

QUALITY. Only OK is a trustworthy fit. LOW_CONFIDENCE: R² below r2_gate. FLAT: slope exactly zero. INSUFFICIENT_HISTORY: fewer than min_train_days daily points; raise AWR retention and wait.

Verify

Drill into one series

SQL*Plus · repo rootyou run
SQL> @report/drill_tbspc.sql SYSAUX            -- name REQUIRED
SQL> @report/drill_tbspc.sql SYSAUX 2482321331 -- ... in one container only

SQL> @report/drill_cpu.sql                     -- BUSY_PCT, all containers
SQL> @report/drill_cpu.sql BUSY_P95
SQL> @report/drill_cpu.sql DB_CPU_PCT 2482321331

SQL> @report/drill_mem.sql                     -- the only database, its only instance
SQL> @report/drill_mem.sql CDB1 2

The two series drills print to screen and spool reports/cap_drill_<name>_<ts>.txt with four blocks:

  • Fit header: slope, intercept, R², the 95% slope CI, days-to-full or days-to-saturation with its WORST/BEST range.
  • Daily series over the train_days window, starting at train_start (so the footer reconciles with the view after a reset): actual, fitted icept + slope · day_n, residual, day-over-day delta, AWR gap, and that day's median / MAD-sigma / threshold / robust z, TRAILING and SAME_DOW side by side.
  • Residual footer: SUM(residual) (zero by construction), and resid_se = sqrt(SSE/(n−2)) and the slope CI re-derived next to the values the view publishes.
  • Anomaly arithmetic: one line per flagged (day, mode) with the CAP_CONFIG knob values.

drill_tbspc.sql requires a tablespace name (without one it prints usage and stops) and ends with who is filling it: the top 10 segments by space allocated over the last seg_window_days (28), with each one's share of the tablespace's growth, from CAPR_SEGMENT_GROWTH over DBA_HIST_SEG_STAT. AWR keeps only the top segments of each snapshot, so a small grower can be missing.

drill_cpu.sql's metric argument defaults to BUSY_PCT; valid values are the six in section 4. Anomalies are scored for BUSY_PCT and DB_CPU_PCT only, so the anomaly columns read n/a for the other four. For those two it adds a block of flagged HOUR_OF_WEEK hours: weekday and hour, baseline size, expected value, sigma and threshold. Both scripts are read-only, never prompt, and UNDEFINE their arguments at the end.

drill_mem.sql [database] [instance] does the same for the memory verdicts of one instance. The database is a dbid or a target name and may be omitted when the schema holds one database; the instance defaults to the only one, else 1. It spools reports/cap_drill_mem_<db>_<instance>_<ts>.txt with five blocks:

  • The instance: memory mode, sga_target, the PGA target and limit, host memory and the evidence window, then the six verdicts with their sentences.
  • The startups of the window: each uptime with its snapshots and hours, and whether its advisor evidence was used or skipped (shorter than mem_min_uptime_hours; its symptoms still count).
  • Every evidence line with value, unit, threshold and direction.
  • The advisor curves: every advised size of each area with the hours and intervals it covers, its cost relative to the reference size, its gain or loss, and marks on the current, reference and suggested sizes.
  • Resize activity: every interval in which a component changed size or counted an operation, then the component summary.
Integrate

Monitoring: alarm on days to full

SQL for an existing monitor (OEM metric extension, Zabbix, Nagios, a scheduler job). Every query only SELECTs. Days to full is computed the same way at every level.

Three ways to feed a monitor
LevelReadThresholdsUse when
1CAPR_TBSPC_DAYS_TO_FULLYours, in the monitorThe monitor holds the alarm rules and needs only the numbers.
2CAPR_ALERTSThe suite's: dtf_warn / dtf_crit, per tablespace in CAP_TBSPC_OVERRIDEThe monitor de-duplicates on its own key and alarms on severity.
3CAPR_ALERTS_LATEST + CAPR_ALERT_EVENTSThe suite's, plus open / resolved state and acksOne page per change (new, escalated, resolved), not one per poll.

Level 1: the numbers, your thresholds

SQL*Pluspoll it
SQL> SELECT db_pdb, tablespace_name,
  2         ROUND(pct_used, 1) pct_used, ROUND(cur_gb, 1) cur_gb, ROUND(limit_gb, 1) limit_gb,
  3         ROUND(slope_mb, 1) mb_per_day,
  4         days_to_full,                   -- point estimate; NULL = not growing or no fit
  5         dtf_worst, dtf_best,            -- the prediction band (worst = soonest)
  6         quality, limit_below_used,
  7         sev_dtf, sev_nearfull,          -- the suite's own verdicts, for comparison
  8         eff_dtf_warn, eff_dtf_crit,     -- thresholds in force for this tablespace
  9         need_gib_30, need_gib_90, add_by_day
 10    FROM capr_tbspc_days_to_full
 11   WHERE is_current = 'Y'
 12   ORDER BY rank_dtf;

-- alarm rule: a trustworthy fit that runs out within 30 days, or a ceiling already under usage
SQL> SELECT db_pdb, tablespace_name, days_to_full, dtf_worst, pct_used
  2    FROM capr_tbspc_days_to_full
  3   WHERE is_current = 'Y'
  4     AND (   (quality IN ('OK', 'CYCLIC') AND NVL(dtf_worst, days_to_full) <= 30)
  5          OR limit_below_used = 'Y');

Alarm only on quality OK or CYCLIC (judged on its per-cycle peaks). INSUFFICIENT_HISTORY, FLAT and LOW_CONFIDENCE fits still have a days_to_full, but not one to page on. Alarm on dtf_worst to page early, or on days_to_full for fewer false alarms. A nearly full tablespace with erratic growth has no reliable fit: also alarm on pct_used or sev_nearfull <> 'OK'. limit_source says where the ceiling comes from (limit_source).

Level 2: the suite's alerts

SQL*Pluspoll it
SQL> SELECT severity, db_pdb, series_key AS tablespace_name,
  2         kind, value, threshold, unit, message, state_key
  3    FROM capr_alerts
  4   WHERE kind IN ('TBSPC_FULL', 'TBSPC_NEARFULL')
  5   ORDER BY sev_rank, value;

TBSPC_FULL: value = days to full, unit DAYS; fires only for a current tablespace with an OK (or CYCLIC peak) fit inside dtf_warn. TBSPC_NEARFULL: percent used, at any fit quality. Map severity (CRIT / WARN) to the monitor's levels; use message as the notification text. De-duplicate on state_key, which is stable while the issue lasts, not on alert_key, which changes daily. Thresholds: Configuration or CAP_TBSPC_OVERRIDE. gated_by in CAPR_TBSPC_DAYS_TO_FULL says why a tablespace did not alert.

Level 3: alert state, one page per change

SQL*Pluspoll it
-- once a day: EXEC cap_results.refresh, or enable CAP_NIGHTLY_JOB (01:00)

-- what is open and not acknowledged
SQL> SELECT severity, db_pdb, series_key, value, message, first_seen, age_days, state_key
  2    FROM capr_alerts_latest
  3   WHERE kind = 'TBSPC_FULL'
  4   ORDER BY sev_rank, value;

-- what changed since the last poll: page on these
SQL> SELECT run_id, event, severity, prev_severity, db_pdb, series_key, message
  2    FROM capr_alert_events
  3   WHERE kind = 'TBSPC_FULL' AND run_id > :last_run_id;

-- silence one for a week (an escalation clears the ack)
SQL> EXEC cap_results.ack('<state_key>', SYSDATE + 7, 'disk ordered, CHG0042')

CAPR_ALERTS_LATEST reads two small tables, so frequent polling is cheap. CAPR_ALERTS and CAPR_TBSPC_DAYS_TO_FULL run the whole view chain on every query; the forecast changes only when AWR adds a day, so poll those hourly or daily. Events: NEW, ESCALATED, DEESCALATED, RESOLVED, REOPENED (Alert state).

i

Stale data. If AWR stops, the forecast freezes and no alerts fire. Alarm on DATA_STALE rows in CAPR_ALERTS (newest snapshot older than stale_hours). At level 3 also alarm on SELECT 1 FROM capr_runs WHERE is_last = 'Y' AND stale_run = 'Y', which returns a row when the nightly refresh has stopped.

For HTTP or Prometheus, the ORDS module in grafana/ publishes the same views and a metrics endpoint (Grafana).

Integrate

Polling CAPR_ALERTS

One row per current issue.

SQL*Plusexample
SQL> SELECT severity, kind, db_pdb, message
  2    FROM capr_alerts ORDER BY sev_rank;

-- alarm on the numbers, without parsing the message text
SQL> SELECT kind, db_pdb, series_key, value, threshold, unit
  2    FROM capr_alerts WHERE severity = 'CRIT';

Columns: severity (CRIT/WARN/INFO) and numeric sev_rank (1/2/3); kind; (dbid, con_dbid) and the db_pdb label; series_key (tablespace, CPU metric or series name); the observation day_dt; the value that crossed threshold, with unit; message; baseline_mode for anomaly kinds (NULL otherwise); alert_key (dbid|con_dbid|kind|series_key|YYYY-MM-DD|mode, unique per row); state_key (kind|dbid|con_dbid|series_key|mode, stable across days, tracked by the results layer); direction (LE for days-to-limit kinds, GE for percent and age kinds, ABS for anomalies and shifts); alarm_threshold (the WARN line, whatever the severity); is_current. An anomaly episode adds first_day, n_days and max_z. Alarm on value vs threshold. Forecast kinds fire only for a current series (is_current = 'Y'); their severity comes from CAPR_SEVERITY, which honours per-tablespace thresholds in CAP_TBSPC_OVERRIDE.

i

Two windows. anomaly_report_days (14, in CAP_CONFIG) bounds the anomaly kinds in CAPR_ALERTS; the anomaly_days argument (30) bounds report sections 3 and 5.

▸

The bitmask decides what pages. Every mode is scored: CAPR_ANOMALIES lists every flagged (point, mode) with alerting = Y or N, and the anomaly rows of CAPR_ALERTS are its alerting = 'Y' rows. To page on HOUR_OF_WEEK as well as SAME_DOW: UPDATE cap_config SET cfg_value = 6 WHERE cfg_name = 'alert_modes_cpu'; (2 + 4). 0 turns a family's anomaly alerts off; the anomalies stay listed.

i

Episodes. Consecutive flagged days of one series and mode are one row: the message starts "N consecutive days, latest …, peak robust z …" and first_day / n_days / max_z carry the numbers. A per-day CPU anomaly inside an active CPU_SHIFT window drops to INFO "(level shift active)".

Integrate

Alert state, acknowledgement and the weekly digest

CAPR_ALERTS is evaluated live and keeps no history. The results layer stores run history, one state per alert, acks and a change feed.

SQL*Plusyou run
SQL> EXEC cap_results.refresh                     -- or enable CAP_NIGHTLY_JOB (daily 01:00)
SQL> SELECT severity, kind, db_pdb, message, age_days, events_since
  2    FROM capr_alerts_latest ORDER BY sev_rank;   -- open, not acked, as of the last run

-- acknowledge: hidden until the date (NULL = until it resolves)
SQL> EXEC cap_results.ack('TBSPC_FULL|3141592653|3141592654|AUDIT_TRAIL|-', SYSDATE + 7, 'disk ordered, CHG0042')
SQL> EXEC cap_results.unack('TBSPC_FULL|3141592653|3141592654|AUDIT_TRAIL|-')

SQL> SELECT * FROM capr_alert_events WHERE run_id > :last_run_id;   -- poll the changes
SQL> SELECT * FROM capr_weekly_digest;                             -- this week vs last

cap_results.refresh records a run in CAP_RUN (RUNNING, then OK, or FAILED with the error stack and re-raised so a scheduler run fails too), copies CAPR_FIT into CAP_FIT_HIST, and merges CAPR_ALERTS by state_key into CAP_ALERT_STATE. Each change writes a CAP_ALERT_EVENT: NEW, ESCALATED, DEESCALATED, RESOLVED (after resolve_grace_runs, 2, runs without it) and REOPENED. It commits; call it with no pending work of your own. ack takes a state_key or the last alert_key the state carried; an escalation or a reopen clears the ack. cap_results.purge(p_keep_days) (default 400) trims old runs; cap_results.reset forgets everything, acks included.

Ceiling

Reading limit_source, and overriding the limit

CAPF_TBSPC_FORECAST and CAPR_TBSPC_FORECAST publish limit_source, the origin of the ceiling days-to-full counts down to:

limit_source values
ValueMeans
OVERRIDESet by a CAP_TBSPC_OVERRIDE row.
AUTOEXTENDThe summed datafile maxsize recorded in AWR. Valid only if the storage underneath can deliver it.
ALLOCATEDNo autoextend; the allocated size is the ceiling.
!

AUTOEXTEND can exceed the storage. A 32 GiB datafile maxsize on a 10 GiB filesystem or ASM diskgroup is not 32 GiB of headroom. Set the real ceiling with an override.

Tune · per tablespace

CAP_TBSPC_OVERRIDE

Set the real ceiling, or exclude a tablespace that is expected to fill. MERGE keeps the statement re-runnable.

SQL*Plusexample
-- the real ceiling is the 200 GiB diskgroup, not the 2 TB datafile maxsize
MERGE INTO cap_tbspc_override t
USING (SELECT 1234567890 AS dbid,
              2345678901 AS con_dbid,
              'APPDATA'  AS tablespace_name,
              200 * 1024 * 1024 * 1024 AS limit_bytes,
              'N'        AS exclude_flag,
              'DG +DATA is 200G; maxsize is fiction' AS note
       FROM   dual) s
ON     (t.dbid = s.dbid AND t.con_dbid = s.con_dbid
        AND t.tablespace_name = s.tablespace_name)
WHEN MATCHED THEN UPDATE
     SET t.limit_bytes  = s.limit_bytes,
         t.exclude_flag = s.exclude_flag,
         t.note         = s.note
WHEN NOT MATCHED THEN
     INSERT (dbid, con_dbid, tablespace_name, limit_bytes, exclude_flag, note)
     VALUES (s.dbid, s.con_dbid, s.tablespace_name,
             s.limit_bytes, s.exclude_flag, s.note);

-- stop forecasting the nightly-truncated staging tablespace, in EVERY database
MERGE INTO cap_tbspc_override t
USING (SELECT 0 AS dbid, 0 AS con_dbid, 'STAGING' AS tablespace_name,
              CAST(NULL AS NUMBER) AS limit_bytes, 'Y' AS exclude_flag,
              'reloaded nightly -- growth is meaningless' AS note
       FROM   dual) s
ON     (t.dbid = s.dbid AND t.con_dbid = s.con_dbid
        AND t.tablespace_name = s.tablespace_name)
WHEN MATCHED THEN UPDATE
     SET t.limit_bytes  = s.limit_bytes,
         t.exclude_flag = s.exclude_flag,
         t.note         = s.note
WHEN NOT MATCHED THEN
     INSERT (dbid, con_dbid, tablespace_name, limit_bytes, exclude_flag, note)
     VALUES (s.dbid, s.con_dbid, s.tablespace_name,
             s.limit_bytes, s.exclude_flag, s.note);

COMMIT;

Tier 2 (OML ESM)

SQL*Plusyou run
SQL> EXEC cap_forecast_ml.train_all(20);       -- top-20 tablespaces + CPU series + their backtest twins
SQL> EXEC cap_forecast_ml.train_tablespace('ORDERS_DATA');   -- retrain one series

Needs the CREATE MINING MODEL privilege (free in all editions since Dec 2019). With esm_tbspc_model at its default AUTO, train_all trains EXSM_HOLT and EXSM_ADDWINTERS(7) holdout twins per tablespace and keeps the one with the lower backtest MAPE. esm_select_by_backtest 0 skips those two trainings and AUTO falls back to Holt; esm_tbspc_model 0 or 1 pins the type. train_all also refreshes the backtest twins of the series it trains (p_backtest => FALSE skips them). Each build runs under a temporary name and replaces the old model only on success; a failure keeps the previous model, records FAILED with last_error in CAP_ML_MODEL, and the procedure raises ORA-20060 after the batch. CAPF_ESM_HEALTH lists every model, the report headers print "N ok, F failed, S stale", and MODEL_HEALTH alerts on it. Daily retraining: Scheduler jobs.

!

Tier 2 stops at +30 days. Oracle 19c hard-caps EXSM_PREDICTION_STEP at 30 at any series length; the package also caps it at a quarter of the series length (90 days of history give a 22-step model). CAPF_COMPARE shows the model's furthest step in the +30 row while the model is at most esm_max_age_days (7) older than its series' last day; section 6 prints the step when it is not +30, and the model age. The +90 / +180 / +365 columns are REGR-only.

Interpret · section 6c

Reading the backtest

Section 6c: each engine forecasts the last backtest_holdout_days (28) from data before the cutoff and is scored against the actuals. MAPE%: mean absolute percentage error, lower is better. BIAS%: signed; positive = over-forecast. BETTER: the engine with the lower MAPE, empty when one of the two has no score. CUTOFF: the day the holdout starts.

ESM_PICK explains the AUTO decision: ADDW H=2.90 W=1.20 (the chosen type, then the Holt and AddWinters MAPEs), or HOLT (config) when esm_tbspc_model pinned the type.

i

REGR needs no models; ESM needs the twins. REGR_MAPE / REGR_BIAS work on a fresh install (CAPF_BACKTEST is always queryable). The ESM columns fill only after cap_forecast_ml.train_backtest. ESM can cover fewer days than REGR: the twins inherit the 19c 30-step cap and the package's FLOOR(rows/4) floor; n_days reports each engine's coverage.

Tune · the estimator

Switching to Theil–Sen or DRIFT

slope_method sets the slope estimator for every CAPF_ fit.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 1 WHERE cfg_name = 'slope_method';
SQL> COMMIT;   -- 0 = OLS (default), 1 = Theil-Sen, 2 = DRIFT

-- ts_slope_bpd is computed only under 1; drift_slope_bpd always
SQL> SELECT tablespace_name, slope_method, ols_slope_bpd, ts_slope_bpd
  2    FROM capf_tbspc_forecast ORDER BY tablespace_name;

0 = OLS (REGR_SLOPE, default), 1 = THEILSEN (median of the pairwise slopes). Theil–Sen resists a one-off step (a bulk load, a migration) that pulls a least-squares line off the trend. The chosen estimator drives the slope, intercept, projections, days-to-full, days-to-saturation, accel_ratio and the FLAT test. Each row's slope_method column says which it used; ols_slope_bpd and ts_slope_bpd stay visible.

i

R² and the prediction bands stay OLS. There is no closed-form Theil–Sen interval in SQL, so r2, resid_se, the projection bands and the slope CI are OLS residual quantities, drawn around the chosen line.

▸

reset_on_shrink. reset_on_shrink (on by default): after the most recent large shrink in a tablespace, the training window restarts at that day (its used_bytes is already post-purge). shrink_mad_k (6) sets how large a drop counts; it is higher than mad_k because it restarts a fit.

Scheduler jobs

Optional, installed separately; setup and the directory-object requirement are in Advanced install.

SQL*Plusyou run
-- every job arrives DISABLED; enable whichever you want
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_NIGHTLY_JOB')   -- daily 01:00: PURGE, RETRAIN, REFRESH, SPOOL
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_COLLECT_JOB')   -- repository mode: hourly cap_repo.collect

SQL> SET SERVEROUTPUT ON
SQL> EXEC cap_nightly('RETRAIN REFRESH SPOOL', 'CAP_REPORTS')

  2    FROM user_scheduler_job_run_details ORDER BY log_date DESC;

CAP_NIGHTLY_JOB calls cap_nightly, which runs the night's steps one after the other in one session, always in this order. PURGE (repository mode) calls cap_repo.purge, which deletes the copies older than repo_retention_days. RETRAIN retrains the Tier 2 models every night, because a model older than esm_max_age_days drops out of the comparison. REFRESH runs cap_results.refresh (Alert state) after the retrain, so the run records tonight's models. SPOOL writes <report_dir>/cap_alerts.txt: a header with the timestamp, database and CRIT/WARN/INFO counts, then one pipe-delimited line per CAPR_ALERTS row, SEVERITY|KIND|DB_PDB|SERIES_KEY|DAY|VALUE|THRESHOLD|UNIT|MESSAGE, or a single OK|NONE|…|No capacity alerts. line. The file name is stable and overwritten on every run.

DEFINE nightly_steps before @install_jobs.sql picks the steps, blank-separated; the order stays fixed. By default the job runs all four, PURGE only in repository mode and SPOOL only when the directory object exists at install time. A failed step is rolled back and the later steps still run. The run then ends FAILED with ORA-20080, which names every failed step. One job cannot overlap itself, so on a large fleet the refresh never runs while the retrain does. CAP_COLLECT_JOB runs beside the nightly job.

i

The SPOOL step writes alerts, not the report. SQL*Plus spooling cannot run inside a scheduler job, so the formatted report comes from cron: report/run_report.sh (CSV and cron). @uninstall_jobs.sql removes the jobs and both procedures and leaves the rest of the suite.
