# grafana/ — Grafana dashboards straight from Oracle (no Elastic)

The second optional way to visualise the suite. Where `elk/` ships documents
into Elasticsearch, this path leaves the data in Oracle: ORDS (Oracle REST
Data Services) exposes a handful of read-only views as JSON, and Grafana's
Infinity data source reads them. Nothing is copied anywhere, nothing writes
to Oracle, and the forecast and anomaly math stays in the views, which is
where the suite keeps it.

```
Oracle   CAPR_SERIES_POINTS / CAPR_HOURLY_POINTS / CAPR_FORECAST_POINTS / CAPR_FIT /
         CAPR_ANOMALIES / CAPR_ALERTS / CAPR_CONTAINER / CAPR_TARGETS /
         CAPR_MEM_VERDICT / CAPR_MEM_EVIDENCE / CAPR_MEM_COMPONENTS /
         CAPR_MEM_COMP_POINTS   (suite views, read-only)
   │
   ▼
ORDS     module awrcap: GET /ords/<schema>/awrcap/{containers,targets,series,hourly,forecast,
   │     fit,anomalies,alerts,mem_verdicts,mem_evidence,mem_components,mem_points,metrics}
   │     protected: a bearer token of an OAuth2 client with the role awrcap_reader
   │     (grafana/ords/awrcap_module.sql; ORDS itself runs anywhere with JDBC access)
   ▼
Grafana  Infinity data source (JSON, OAuth2 client credentials) + four provisioned dashboards
         (grafana/provisioning, grafana/dashboards, generated by grafana/build_*.py)
```

The endpoint contract is in [`API.md`](API.md). The same point views feed
`elk/export_capacity.sql` (all but `CAPR_HOURLY_POINTS`, which only this path
serves), so both paths show the same numbers by construction.

## When to pick this over `elk/`

- You have Grafana (or want it) and no Elastic stack.
- You want nothing between the dashboards and the database: every refresh
  is a live query against the views, so a new AWR snapshot shows up as soon
  as the daily views see it.
- You are fine running ORDS. It needs a JDBC route to the database and a
  one-time install that creates its own schemas (`ORDS_METADATA`,
  `ORDS_PUBLIC_USER`) in the container that holds the suite.

Pick `elk/` instead when the fleet is already in Elastic, when you want
history of the fits themselves (the ELK path snapshots fits and alerts per
day; this path shows the current fit only), or when ORDS is not an option.

## Install

1. **Suite views.** Already part of `install.sql` (`ddl/45_report_views.sql`,
   `ddl/55_report_views_ml.sql`). Reinstall the suite if it predates them.
2. **ORDS.** Install and run ORDS against the database. The lab recipe, with
   a dedicated installer user instead of SYS and ORDS in Docker, is in
   [`ords/README.md`](ords/README.md).
3. **REST module.** As the schema owner (or as a DBA with `ORDS_ADMIN`):
   ```
   SQL> @grafana/ords/awrcap_module.sql
   ```
   This ORDS-enables the schema and defines the `awrcap` module, protected
   by the ORDS privilege `awrcap.read`. Re-run to update;
   `awrcap_module_drop.sql` removes the module, the privilege, the role and
   the client. `install.sh` with `ORDS=Y` runs the same script, protected.
4. **Client.** Create the OAuth2 client Grafana signs in with and put its id
   and secret into the gitignored `grafana/.env`. The script prints them
   once, so send its output to the file, not to the screen:
   ```
   (umask 077; sqlplus -S -L / @grafana/ords/awrcap_client.sql | grep '^ORDS_CLIENT_' >> grafana/.env)
   ```
   `grafana/.env` then holds `ORDS_CLIENT_ID` and `ORDS_CLIENT_SECRET`. Run
   it again to replace the client (remove the two old lines first).
5. **Grafana.** Set `GF_ADMIN_PASSWORD` in the gitignored `grafana/.env`
   first: the compose file stops without it, and Grafana applies it when it
   initialises an empty data volume. `docker compose -f
   grafana/docker-compose.yml up -d` starts Grafana (port 3001, Infinity
   plugin preinstalled, data source and dashboards provisioned from this
   directory, user `admin` with that password, anonymous read-only viewing
   on) and ORDS (host port 8181, `ORDS_HOST_PORT` overrides). Point an existing Grafana at the same files instead if you
   have one: copy `provisioning/` and `dashboards/`, install the Infinity
   plugin, and set `ORDS_URL` to your module's base URL, `ORDS_TOKEN_URL` to
   `<ords>/ords/<alias>/oauth/token` and the two client variables.

Open `http://<grafana>:3001/d/awrcap-tablespaces`, `/d/awrcap-cpu-series`,
`/d/awrcap-fleet-anomalies`, `/d/awrcap-memory`. The four boards link to
each other and carry the target, database and series selection across.

## How the boards are built

Each dashboard is generated by a `build_*.py` (stdlib only) on top of
`dash_lib.py`. The Target variable lists the suite's targets and narrows the
Database variable; panels filter on the database label alone, and every
table has a Target column. The CPU and workload series board draws one panel
per workload series, `IOPS` and `IO_MBPS` included. The memory board shows
the verdicts, their evidence and the SGA components (`mem_*` endpoints);
its rows are instance level, so they belong to a database's root container.
To show a new column of an endpoint, add it to the handler's `SELECT` in
`grafana/ords/awrcap_module.sql` and to the panel's column list; a string
column also joins `STRING_COLS` in `dash_lib.py`. Every panel is an Infinity JSON query against one endpoint
with `${__from:date:iso}` / `${__to:date:iso}` and the `$db` / `$series`
variables; long rows are turned into one series per `db + series` with
Grafana's partition transformation, and forecast / band / ceiling series are
styled by name (dashed, dotted, grey). Anomalies arrive three ways: a
dashboard annotation query on `anomalies` (red vertical markers with the
message on hover, a shaded span for a level shift), red points on the
observed line where `anomaly = 1`, and red bars in the daily-growth panel.
Every anomaly row carries its baseline mode (`TRAILING`, `SAME_DOW`,
`HOUR_OF_WEEK`); the fleet board filters on it and colours its per-day bars
by it, and the CPU board's hourly panel draws the `hourly` endpoint with the
usual value for each hour of the week and the flagged hours in red. All
timestamps are the DB wall clock labelled `Z`; the boards run in UTC so they
show it unshifted (API.md).
Panels that need the same endpoint reuse each other's result through the
Dashboard data source, which keeps a page load to about a dozen ORDS calls.

## Security

The module is protected. The ORDS privilege `awrcap.read` covers it and
requires the ORDS role `awrcap_reader`, so every handler, `metrics`
included, answers 401 without a bearer token. A reader is an OAuth2 client
with the grant type `client_credentials` that holds the role
(`grafana/ords/awrcap_client.sql`); it exchanges its id and secret for a
token at `/ords/<alias>/oauth/token`. The Infinity data source does that
exchange and renews the token (`provisioning/datasources/infinity.yml`). Its
health check reads `containers`, so it fails when the client is wrong.
[`API.md`](API.md) "Access" has the calls.

Why OAuth2 client credentials and not ORDS basic auth with a database user:
it needs no database account and no password of one in Grafana, the secret
is stored hashed and can be replaced without touching a schema, and both
Infinity and Prometheus speak it.

- The client id and secret live only in the gitignored `grafana/.env`. No
  tracked file holds them.
- Over plain HTTP the secret and the token travel unencrypted. Outside a
  lab put ORDS behind TLS.
- The compose file keeps Grafana's anonymous viewer access. Whoever reaches
  Grafana reads the boards without the ORDS client. Turn
  `GF_AUTH_ANONYMOUS_ENABLED` off where that matters.
- Opt-out for a closed lab: `@grafana/ords/awrcap_module.sql <schema> - PUBLIC`
  removes the privilege, and `ORDS_AUTH_METHOD=none` in `grafana/.env` tells
  the data source to send no token. Anyone who reaches the ORDS port then
  reads every handler.

The views expose capacity numbers and object names, never row data.

## Notes and limits

- **One schema per module.** The endpoints serve the schema the module is
  defined in, so a board shows the databases that schema's seam presents:
  every target its repository has registered, with their PDBs (one CDB for
  a standalone install, which is its own target). For several repositories,
  define the module in each and add one Infinity data source per
  repository, or register the databases in one repository.
- **Live queries.** Every refresh runs the CAPF_/CAPA_ views, whose
  self-joins and ESM lookups take seconds at fixture size (forecast and
  anomalies endpoints: 5 to 7 s here; a full board fills in 10 to 20 s).
  That is the price of having no copy; put a result cache or materialized
  views under `CAPR_*_POINTS` if it matters, or use `elk/` which snapshots.
- **ORDS concurrency.** The default pool refuses bursts (HTTP 429/555 beyond
  roughly ten in-flight requests). Raise `jdbc.MaxLimit` in the pool config
  for many simultaneous viewers.
- **Single-value filters.** `db` and `series` take one value server-side;
  multi-select and "All" are filtered inside Infinity after fetching the
  kind.
- **No fit history.** `fit` is the current fit only. The ELK path keeps a
  daily snapshot of fits and alerts; this path does not.
- **Memory endpoints are slow.** `mem_verdicts` and `mem_evidence` read a
  30-day window of AWR memory history on every request and take far longer
  than the other endpoints. The data source waits up to five minutes
  (`timeoutInSeconds`); the memory board loads last.
- **Lab only.** Anonymous viewer access is convenient on a workstation and
  wrong anywhere else; see Security above.

## Regenerating the dashboards

`grafana/dashboards/*.json` is generated; edit the `build_*.py` builder and
re-run it. Grafana's file provisioner picks changes up within its scan
interval.
